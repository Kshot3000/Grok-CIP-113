# PRISM · Cardano programmable token studio

**Your asset. Your rules.** An open-source workspace for exploring CIP-113 programmable assets, real-world finance, and privacy-aware eligibility.

Built by **[KShot · @kshot9000](https://x.com/kshot9000)** for the Cardano community.

**[Open the website](https://kshot3000.github.io/Grok-CIP-113/)** · **[CIP-113 specification](https://github.com/cardano-foundation/CIPs/tree/master/CIP-0113)** · **[Report an issue](https://github.com/Kshot3000/Grok-CIP-113/issues)**

| Token studio | Six editable templates — real-world asset, private credit, stablecoin concept, community access, carbon credit (indivisible tonnes, KYC-gated), and event ticket (open access with a four-per-transfer anti-scalping cap) — validated token identity and precision, configurable allowlist / transfer cap / issuer controls / eligibility, and exact BigInt transfer modeling. A supply sequence panel chains changes in order against a running modeled supply, so a burn creating int64-ceiling headroom a later mint can use (and a blocked change leaving the supply intact for later steps) is visible step by step; a custom builder sits next to its presets — start from the preset you were viewing, then change actions, actors, and amounts, add steps (up to 12), reorder them, or remove them, and run your own issuance schedule against the same model. ## The boundary of this release

**This is a design and research workspace, not a token issuer, lending platform, or deployed ZK application.**

- CIP-113 was present in the upstream repository when checked on **2026-10-04**, with frontmatter status **Proposed**. A merged specification is not a network-wide deployment or certification.
- PRISM’s manifest is an application-specific design format. It is **not** a CIP-defined registry datum, compiled Plutus blueprint, token policy, signed transaction, or minted asset. The registry entry preview is likewise application-specific: it contains no policy ID, datum encoding, or on-chain registration.
- Transfer and eligibility tests run in JavaScript. They do not execute on-chain scripts, check spendable balances, verify identity, or generate zero-knowledge proofs.
- The Midnight wallet connector is real. A Compact circuit, deployed contract, proof service, issuer / revocation system, and Cardano attestation verifier are **not deployed** by PRISM.
- PRISM has no affiliation with RealFi, Midnight, or the Cardano Foundation. RealFi interactions happen at [app.realfi.co](https://app.realfi.co/); scenario rates are fictional inputs, not product rates.
- No wallet transaction signing, message signing, transaction submission, asset custody, minting, redemption, staking, or payment initiation is implemented.
- The Foundation’s reference platform identifies itself as R&D with an independent security audit pending. Review and pin all dependencies before implementing a production system.

## Run locally

Requires Node.js 22 or newer. There are **no npm dependencies and no install step**.

```sh
git clone https://github.com/Kshot3000/Grok-CIP-113.git
cd Grok-CIP-113
npm test
npm run dev
```

Open `http://localhost:4173`. Run `npm run build` for a static `dist/` directory. The site supports a repository subpath and uses hash navigation, so deep links work on GitHub Pages without server rewrites.

## GitHub Pages

The included workflow runs tests, builds the site, and publishes `dist/` on pushes to `main`.

If this is the first deployment, set **Settings → Pages → Source → GitHub Actions**. The workflow also requests automatic enablement; if repository permissions prevent that, enable Pages in settings and rerun the workflow. No personal access token or paid service is needed.

## Configuration

`src/config.js` contains creator identity, the donation address, verified source URLs, network endpoints, and optional registry API configuration. Change the `site` URL if hosting elsewhere.

`registryApi` is intentionally empty. To enable registry reads, set it to the HTTPS origin of your hosted, Foundation-compatible programmable-token backend, with CORS for your site. PRISM calls the read-only `GET /api/v1/registry/protocols` endpoint and validates its basic response shape. An indexer is authoritative only for the deployments and network it actually indexes; independently verify deployment identity.

Do not put Blockfrost tokens, mnemonics, signing keys, or service secrets in frontend configuration. This website needs none.

## Data, privacy, and networks

- Network data comes directly from Koios for the selected network. Failed requests display an unavailable state; old or fictitious values are not presented as live. A block older than five minutes is labeled delayed.
- The Preview reference is repository configuration, not an assertion that an address is safe, current, funded, or deployed. The bundled reference was checked on 2026-10-03 and is explicitly marked as a snapshot if refresh fails.
- A Cardano wallet exposes mainnet versus testnet via CIP-30. It cannot establish which testnet the user selected. Confirm Preview versus Preprod in the wallet.
- Wallet state is kept in memory. Only a valid design is saved to local storage. No analytics or tracking cookies are included. Local draft persistence may be unavailable in restricted browser modes; JSON export remains available.
- The eligibility sandbox does not save or transmit its fictional input values. Do not enter real personal data.
- Public API providers and external sites receive ordinary network requests when used. Wallet permission is requested only after a user chooses to connect. App disconnection clears PRISM state; revoke permissions inside the wallet to fully remove access.
- Donation copy and QR contain the exact user-supplied Cardano mainnet address. PRISM never initiates the transfer.

Tests cover exact amount precision, denial paths, malformed imports, UTF-8 token name limits, collateral calculations, eligibility thresholds, Bech32 checksums, official CIP-19 vectors, original-payment-credential ownership, wallet network / account changes, Midnight API compatibility, and malformed API data. A dedicated substandard suite covers every documented denial path of the modeled modules — denylisted sender/recipient, seizure authority, each KYC certificate check failing independently, allowlist membership and entry expiry, the self-transfer exemption — plus template presets, manifest round-trips, and legacy-manifest defaults. A registry-preview suite guards the Export step’s datum preview: exact base units at multiple precisions, determinism (no timestamps), faithful policy/substandard reflection, the still-required deployment fields, and a hard ban on policy-ID / datum-hash / CBOR fields ever appearing in the preview. A learn suite guards the status tracker and learning path — Proposed status, all four spec acceptance criteria unchecked, every core concept covered, and no overclaiming language. A wallet-hardening suite guards the connection layer: expected-network naming, malformed network ids, incomplete CIP-30 / Midnight APIs, malformed public addresses, Midnight account-change detection, and per-network session re-verification. A wallet-address-book suite guards the connected wallet's local address summary: CIP-19 reward-address decoding (key and script credentials, hex and bech32, payment addresses and malformed input rejected), unique used-address counts by kind with duplicates counted once, the CIP-113 smart-wallet shape count, wrong-network entries flagged and unreadable entries counted rather than thrown, the reward credential matching or differing from the payment addresses' stake credential (null for an enterprise change address), unavailable lists reported as null counts instead of guesses, and the connection-level guarantees — a full wallet yields a book, a minimal wallet connects with none, and a list method that throws leaves that list unavailable without failing the connection. A manifest-integrity suite guards the import path: exact string amounts beyond float precision, rejection of numeric amounts and of any token-summary field that disagrees with the design, rejection of forged deployment / proof / affiliation claims, and backward compatibility for genuine and legacy exports. A RealFi amortization suite checks the schedule model against textbook values (a $10,000 loan at 12% APR over 12 months repays $888.49 a month and $661.85 of interest), exact principal repayment with a zero final balance at 0%, short, and 30-year terms, the declining interest/principal split, and rejection of invalid or fractional-month terms. An extra-payment suite guards the payoff model on the same schedule function: no extra reproduces the baseline schedule exactly, $1,000 extra on the default scenario pays it off in 10 months (2 early) with a smaller final payment and $391.62 less interest, principal parts still sum exactly to the principal with an extra, a zero rate shortens the term and saves nothing, an extra larger than the loan pays it off in month one with a single month of interest, a larger extra never pays off later or costs more, the extra reaches principal from month one, and invalid extra amounts are rejected. A payoff-target suite guards the inverse solver: a full-term target needs no extra and reproduces the baseline exactly, the solved extra for a 10-month target on the default scenario is $835.74 (less than the $1,000 known to work, and one cent less verifiably misses the target across five targets), feeding the solved extra back into the schedule reproduces the solver's result exactly, earlier targets never need less or save less, a zero rate solves by exact division, a one-month target carries a single month of interest, and invalid targets and loans are rejected. A refinance suite guards the comparison model: the default scenario at half the rate with $500 costs saves $603.11 overall with a durable break-even in month 6, net benefit is exactly the total-cost difference with closing costs counted and never financed (the new loan's principal parts sum to the remaining balance alone), the balance and remaining schedule are the displayed schedule's own rows after the payments made, a first-crossing break-even that later evaporates (refinancing six payments in over a fresh 12 months) returns no break-even and a $457.58 loss, a term stretch at the same rate lowers the payment while costing more overall, a higher rate never breaks even, identical zero-cost terms are an exact wash, and invalid payments-made / costs / new terms are rejected. A collateral-stress suite guards the RealFi stress model: at no drop it reproduces the credit scenario exactly, the ceiling-breach drop (10.71% on the default scenario) and the drop to par (37.5%) are exact — at the breach drop the stressed ceiling equals the principal and any further fall breaches — a 25% drop values the default collateral at $60,000 with an 83.33% loan-to-value, an $8,000 shortfall, and an $11,428.57 top-up measured against the required collateral (feeding that top-up back restores a zero headroom), the standard-drop table is monotone, a scenario starting above its ceiling is already breached while one exactly on it is within at 0% and breached by any fall, drop-to-par is null once the principal exceeds the collateral, and invalid drops and scenario inputs are rejected. A rate-stress suite guards the payment-side stress model: a zero rise reproduces the displayed schedule exactly, the shock is in percentage points (8% + 3 points is 11%, with a $4,419.08 payment and $835.94 more interest on the default scenario), every shocked figure is the schedule's own figure at that rate, the standard-rise table is monotone and omits rises past the 100% modeled limit, the budget solver's rate fits while one hundredth of a point higher does not (a $4,500 budget carries the default scenario to 14.45%), a budget equal to the current payment solves back to about the current rate, a budget below it reports negative headroom, a budget below the 0% payment fits no rate, a budget fitting even 100% is reported as capped, and invalid rises, budgets, and scenario inputs are rejected. A debt-service coverage suite guards the income-side model: coverage divides the supplied income by the displayed schedule's own payment (1.38× on the default scenario at $6,000 a month), the income needed at the reader-chosen 1.25× requirement is $5,436.78 with a $563.22 cushion, the income could fall exactly 9.39% before coverage reaches the requirement (feeding the fallen income back lands on the requirement), income exactly at the requirement meets it with zero tolerance and the principal solver returns the scenario's own $50,000 — distinct from income below it, which reports a $436.78 shortfall, zero tolerance, and a smaller carryable principal — the largest principal the income can carry fits its allowable payment while one cent more of principal does not ($55,179.75 at the default), the standard-requirement table is monotone in the income needed and flips from meets to falls-short where the income sits, a 0% loan solves by exact division, an income fitting even the modeled principal limit is reported as capped, and invalid incomes, ratios, and scenario inputs are rejected. A balloon-payment suite guards the term-structure model: the balloon is exactly the displayed schedule's own balance after the due month's payment (never re-derived), the default scenario due at month 6 leaves $25,498.27 — 51.00% of the principal — in the balloon with a $29,847.70 final payment, paying it in full totals exactly principal plus the interest actually charged ($1,594.80, with $598.25 of full-term interest not charged), a due month at the end of the amortization period is the plain amortizing loan with identical totals, due in month 1 charges exactly one month of interest with 91.97% of the principal riding on the final payment, a 0% loan solves by exact division, a 30-year amortization due in 5 years keeps 93.05% of the principal in the balloon, the quarter-point due-month table ends at zero, an earlier due month always means less interest and a larger balloon share, and invalid due months, amortization periods, and scenario inputs are rejected.
