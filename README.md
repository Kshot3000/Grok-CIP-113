# PRISM · Cardano programmable token studio

**Your asset. Your rules.** An open-source workspace for exploring CIP-113 programmable assets, real-world finance, and privacy-aware eligibility.

Built by **[KShot · @kshot9000](https://x.com/kshot9000)** for the Cardano community.

**[Open the website](https://kshot3000.github.io/Grok-CIP-113/)** · **[CIP-113 specification](https://github.com/cardano-foundation/CIPs/tree/master/CIP-0113)** · **[Report an issue](https://github.com/Kshot3000/Grok-CIP-113/issues)**

## What works

| Workspace | Functionality |
| --- | --- |
| Token studio | Six editable templates — real-world asset, private credit, stablecoin concept, community access, carbon credit (indivisible tonnes, KYC-gated), and event ticket (open access with a four-per-transfer anti-scalping cap) — validated token identity and precision, configurable allowlist / transfer cap / issuer controls / eligibility, and exact BigInt transfer modeling. The Test step also has a sequence lab: transfers run in order against a modeled ledger (the issuer starts holding the full designed supply), each step checked for sender balance, access, the per-transfer cap, issuer controls, and eligibility — a blocked step moves nothing and later steps are still evaluated, so the knock-on effect of a denial is visible in the final balances. A custom builder sits next to the presets: start from the preset you were viewing, then change senders, recipients, and amounts, add steps (up to 12), reorder them, or remove them, and run your own order against the same modeled ledger. |
| Substandard lab | Each template presets a CIP-113 Layer-3 substandard — freeze-and-seize, KYC, or KYC extended from the Foundation reference platform (community template uses PRISM’s generic rules). The Test step models the modules’ documented checks one by one: denylist on both parties, authorised-only seizure, the five sender-certificate checks, recipient allowlist membership and expiry, and the self-transfer exemption. Local simulation only; legacy design files without a substandard import as generic. |
| Supply lab | The Test step also models supply changes (issuance): the designed supply is an *initial* supply, so the lab runs a mint or a burn attempted by the issuer or by someone else, checked for issuance authority and for exact BigInt supply bounds — a mint may not pass the signed 64-bit asset ceiling (landing exactly on it is allowed, one base unit past it is blocked) and a burn may not exceed what was issued (burning the whole supply ends at exactly zero). The per-transfer cap is deliberately *not* applied: it gates transfers, not issuance. Labeled in the UI as PRISM's generic issuance model — not a Foundation substandard module, and a real token's issuance logic defines its own authority. No tokens are minted or burned. A supply sequence panel chains changes in order against a running modeled supply, so a burn creating int64-ceiling headroom a later mint can use (and a blocked change leaving the supply intact for later steps) is visible step by step; a custom builder sits next to its presets — start from the preset you were viewing, then change actions, actors, and amounts, add steps (up to 12), reorder them, or remove them, and run your own issuance schedule against the same model. A timeline lab then interleaves the two: transfer steps and supply steps run in one order against one modeled state — a ledger of balances plus the supply those balances always sum to — so minted tokens become transferable in the same timeline, and a burn draws on the issuer's modeled holding (tokens already distributed to other modeled accounts are not the issuer's to burn, so a burn can be blocked by the issuer's balance even when the total supply would cover it). Transfer rules gate only the transfer steps and issuance checks only the supply steps; a blocked step changes nothing and later steps still evaluate. A custom builder sits next to its presets — start from the preset you were viewing, then change step kinds (switching a kind converts the step, keeping its amount), senders, recipients, actions, actors, and amounts, add transfer or supply steps (up to 12), reorder them, or remove them, and run your own timeline against the same one-state model. |
| Learn CIP-113 | A six-lesson plain-language learning path paraphrased from the official spec — why programmable tokens exist, shared-custody smart wallets, the withdraw-zero pattern, the registry, substandards, and third-party actions / unfracking — each lesson naming its spec section. Plus a status tracker reproducing the spec’s frontmatter and its own “Path to Active” acceptance checklist verbatim (all four boxes unchecked while the status is Proposed), with the Foundation reference’s R&D / audit-pending caveat kept in place. Status snapshot re-verified against upstream on 2026-10-04. |
| Design review | The Design step ends with a live local review of the design's own coherence, recomputed on every edit: validation blockers, rule coverage (a design with no active rules warns it behaves like an ordinary native token), cap effectiveness (a cap equal to the whole supply warns it can never block a transfer; otherwise the cap's exact BigInt share of supply is shown), the pause state the design would start in, alignment between the generic toggles and the chosen substandard's documented checks (KYC extended expects a recipient allowlist; basic KYC checks the sender only), supply headroom against the signed 64-bit ceiling, and indivisibility at 0 decimals. Labeled in the UI as a local review — not a security audit, not validator review, and no guarantee a design is safe or deployable. |
| Design files | Local draft persistence, versioned JSON export, validated import, and developer handoff. Imports are integrity-verified: amounts must be exact decimal strings (JSON numbers are rejected outright — JSON parsing would round them past 2⁵³ and silently change the supply), the token summary must match the design field by field, and a manifest claiming a deployed status, an Active CIP-113, a verified Midnight proof, a deployed bridge, or a RealFi affiliation/product is rejected instead of imported. Files whose status/implementation sections were hand-trimmed away still import; whitespace around names and amounts is canonicalised. No server account is required. |
| Registry entry preview | The Export step also renders a deterministic, application-specific preview of the design information a CIP-113 registry entry would need to describe — token identity, exact BigInt base units, transfer policy, and substandard — alongside an explicit list of what only a real deployment can supply (policy ID, registry node position and proofs, Plutus Data / CBOR encoding). Labeled “NOT A CIP DATUM” in the UI; PRISM registers nothing. |
| Cardano wallets | Real CIP-30 discovery and permission flow, network checks that name the expected network (CIP-30 reports only mainnet vs testnet, so Preview vs Preprod is confirmed in the wallet), rejection of malformed network ids and incomplete wallet APIs, public payment address, account-change detection, and app disconnection. Read only. |
| Network explorer | Live Koios chain tip and native asset lookup, refresh and failure states, no invented metrics. The registry panel can also verify the Foundation’s pinned Preview reference deployment live: the platform repository’s configuration is fetched fresh and must match the pinned script hash and protocol policy field by field, and Koios Preview must confirm that exact deployment transaction in a block with valid contract execution, before anything is shown as confirmed. Registry browsing still requires a Foundation-compatible indexer, which is not connected. |
| Smart-wallet tool | Actual CIP-19 Bech32 validation and CIP-113 address derivation using the original payment credential as owner. Optional Foundation Preview reference with explicit snapshot fallback. A derived address is immediately decoded back underneath the result, so its payment script hash and owner credential can be checked field by field. |
| Address inspector | The Network explorer also decodes any Shelley address locally (no lookup): CIP-19 header type (base / enterprise), mainnet vs testnet, the exact payment and stake credential hashes (key or script), and whether the address matches the CIP-113 smart-wallet *shape* — a base address whose payment credential is a script hash, with the owner's original payment credential in the stake position. The result states plainly that shape alone does not prove CIP-113 membership: that requires the payment hash to equal a deployed base script hash and the token to appear in that deployment's registry. Byron, pointer, and reward addresses are rejected with the same messages as derivation. |
| Asset fingerprint | The asset lookup also computes the asset's CIP-14 fingerprint locally — a dependency-free BLAKE2b (RFC 7693) implemented in `src/cardano.js`, digesting policy ID ‖ asset name to blake2b-160 and Bech32-encoding it under the `asset` prefix — live as the policy ID and asset name are typed, with no network needed. When Koios answers, its reported fingerprint is cross-checked against the local computation: agreement is shown, a mismatch is flagged as do-not-rely-on-this-result, and a missing Koios fingerprint is stated rather than silently filled in. The fingerprint identifies an asset; the UI states it does not prove authenticity, backing, or registry membership. The implementation is pinned by all eight test vectors published in CIP-0014 plus multi-block BLAKE2b digests cross-checked against a reference implementation. |
| RealFi lab | A simple-interest and collateral scenario calculator, plus an amortized repayment schedule for the same scenario — equal monthly payments with interest charged on the declining balance, compared line by line against the simple-interest total — and an optional extra monthly payment modeled on top of that schedule: the same extra every month, all of it to principal, showing the earlier payoff month, the months saved, and the exact interest saved against the no-extra schedule (assuming no prepayment penalty, which a real agreement's own terms would govern) — plus links to RealFi’s official USDrf / sUSDrf app. |
| Midnight privacy | Real DApp Connector API v4 wallet discovery, selected-network connection, and public unshielded address. The live session is re-verified on focus and every minute against the selected network’s Midnight id, and an account switch in the wallet now disconnects PRISM instead of silently showing the old address. Local fictional eligibility sandbox, plus a cohort preview: five fictional participants — each built to isolate one policy check — evaluated against the sandbox's public policy, showing only the public output a verifier would get (decision + which public checks passed), never the private scores, ages, or region status behind it. |
| Community | Branded Open Graph / X share image (1200 × 630 JPEG, ~89 KB since v1.8), X sharing draft, source links, creator profile, donation address copy and locally generated QR. |
| Accessibility & discovery | Modal dialogs manage focus properly: focus moves into the dialog when it opens and returns to the button that opened it when it closes (including on Escape), on top of the existing skip link, tab keyboard support, focus-visible outlines, and reduced-motion support. Search and social discovery is honest and machine-readable: schema.org WebApplication JSON-LD (no ratings, reviews, or affiliation claims), a `robots.txt`, and a `sitemap.xml` that lists only the canonical URL — the app’s hash routes are views of one document, not separate pages. |

## The boundary of this release

**This is a design and research workspace, not a token issuer, lending platform, or deployed ZK application.**

- CIP-113 was present in the upstream repository when checked on **2026-10-04**, with frontmatter status **Proposed**. A merged specification is not a network-wide deployment or certification.
- PRISM’s manifest is an application-specific design format. It is **not** a CIP-defined registry datum, compiled Plutus blueprint, token policy, signed transaction, or minted asset. The registry entry preview is likewise application-specific: it contains no policy ID, datum encoding, or on-chain registration.
- Transfer and eligibility tests run in JavaScript. They do not execute on-chain scripts, check spendable balances, verify identity, or generate zero-knowledge proofs.
- The Midnight wallet connector is real. A Compact circuit, deployed contract, proof service, issuer / revocation system, and Cardano attestation verifier are **not deployed** by PRISM.
- PRISM has no affiliation with RealFi, Midnight, or the Cardano Foundation. RealFi interactions happen at [app.realfi.co](https://app.realfi.co/); scenario rates are fictional inputs, not product rates.
- No wallet transaction signing, message signing, transaction submission, asset custody, minting, redemption, staking, or payment initiation is implemented.
- The Foundation’s reference platform identifies itself as R&D with an independent security audit pending. Review and pin all dependencies before implementing a production system.

## Run locally

Requires Node.js 22 or newer. There are **no npm dependencies and no install step**.

```sh
git clone https://github.com/Kshot3000/Grok-CIP-113.git
cd Grok-CIP-113
npm test
npm run dev
```

Open `http://localhost:4173`. Run `npm run build` for a static `dist/` directory. The site supports a repository subpath and uses hash navigation, so deep links work on GitHub Pages without server rewrites.

## GitHub Pages

The included workflow runs tests, builds the site, and publishes `dist/` on pushes to `main`.

If this is the first deployment, set **Settings → Pages → Source → GitHub Actions**. The workflow also requests automatic enablement; if repository permissions prevent that, enable Pages in settings and rerun the workflow. No personal access token or paid service is needed.

## Configuration

`src/config.js` contains creator identity, the donation address, verified source URLs, network endpoints, and optional registry API configuration. Change the `site` URL if hosting elsewhere.

`registryApi` is intentionally empty. To enable registry reads, set it to the HTTPS origin of your hosted, Foundation-compatible programmable-token backend, with CORS for your site. PRISM calls the read-only `GET /api/v1/registry/protocols` endpoint and validates its basic response shape. An indexer is authoritative only for the deployments and network it actually indexes; independently verify deployment identity.

Do not put Blockfrost tokens, mnemonics, signing keys, or service secrets in frontend configuration. This website needs none.

## Data, privacy, and networks

- Network data comes directly from Koios for the selected network. Failed requests display an unavailable state; old or fictitious values are not presented as live. A block older than five minutes is labeled delayed.
- The Preview reference is repository configuration, not an assertion that an address is safe, current, funded, or deployed. The bundled reference was checked on 2026-10-03 and is explicitly marked as a snapshot if refresh fails.
- A Cardano wallet exposes mainnet versus testnet via CIP-30. It cannot establish which testnet the user selected. Confirm Preview versus Preprod in the wallet.
- Wallet state is kept in memory. Only a valid design is saved to local storage. No analytics or tracking cookies are included. Local draft persistence may be unavailable in restricted browser modes; JSON export remains available.
- The eligibility sandbox does not save or transmit its fictional input values. Do not enter real personal data.
- Public API providers and external sites receive ordinary network requests when used. Wallet permission is requested only after a user chooses to connect. App disconnection clears PRISM state; revoke permissions inside the wallet to fully remove access.
- Donation copy and QR contain the exact user-supplied Cardano mainnet address. PRISM never initiates the transfer.

## Project layout

```text
src/app.js          UI, routes, local persistence, and interactions
src/domain.js       Exact-quantity token rules and scenario models
src/cardano.js      Bech32 address validation and smart-wallet derivation
src/services.js     Live APIs and read-only wallet adapters
src/config.js       Identity, endpoints, templates, and source references
src/learn.js        CIP-113 learning path and status-tracker data (spec-sourced)
src/a11y.js         Modal focus management (capture invoker, focus in, restore on close)
src/styles.css      Responsive visual system and accessibility states
tests/             Meaningful domain and integration-boundary tests
scripts/           Dependency-free build and local server
docs/              Integration handoff and launch copy
```

Tests cover exact amount precision, denial paths, malformed imports, UTF-8 token name limits, collateral calculations, eligibility thresholds, Bech32 checksums, official CIP-19 vectors, original-payment-credential ownership, wallet network / account changes, Midnight API compatibility, and malformed API data. A dedicated substandard suite covers every documented denial path of the modeled modules — denylisted sender/recipient, seizure authority, each KYC certificate check failing independently, allowlist membership and entry expiry, the self-transfer exemption — plus template presets, manifest round-trips, and legacy-manifest defaults. A registry-preview suite guards the Export step’s datum preview: exact base units at multiple precisions, determinism (no timestamps), faithful policy/substandard reflection, the still-required deployment fields, and a hard ban on policy-ID / datum-hash / CBOR fields ever appearing in the preview. A learn suite guards the status tracker and learning path — Proposed status, all four spec acceptance criteria unchecked, every core concept covered, and no overclaiming language. A wallet-hardening suite guards the connection layer: expected-network naming, malformed network ids, incomplete CIP-30 / Midnight APIs, malformed public addresses, Midnight account-change detection, and per-network session re-verification. A manifest-integrity suite guards the import path: exact string amounts beyond float precision, rejection of numeric amounts and of any token-summary field that disagrees with the design, rejection of forged deployment / proof / affiliation claims, and backward compatibility for genuine and legacy exports. A RealFi amortization suite checks the schedule model against textbook values (a $10,000 loan at 12% APR over 12 months repays $888.49 a month and $661.85 of interest), exact principal repayment with a zero final balance at 0%, short, and 30-year terms, the declining interest/principal split, and rejection of invalid or fractional-month terms. An extra-payment suite guards the payoff model on the same schedule function: no extra reproduces the baseline schedule exactly, $1,000 extra on the default scenario pays it off in 10 months (2 early) with a smaller final payment and $391.62 less interest, principal parts still sum exactly to the principal with an extra, a zero rate shortens the term and saves nothing, an extra larger than the loan pays it off in month one with a single month of interest, a larger extra never pays off later or costs more, the extra reaches principal from month one, and invalid extra amounts are rejected. A templates suite pins the whole template catalog: unique ids and tickers, a zero-error design from every template, a real icon and accent style for each (no silent fallback box or unstyled card), manifest round-trips for the carbon-credit and event-ticket templates, and their promised behaviour — indivisible tonnes with the KYC gate and cap, the four-per-transfer anti-scalping cap, and the organizer pause. Wallet unit tests use explicit mocks; they do not claim live wallet-extension or chain transactions. A craft suite guards the v1.8 accessibility/discovery layer: the modal focus helpers against mock elements (invoker capture, first-focusable targeting, restore only while still connected), the JSON-LD block (parseable, pointing at the canonical site and the creator, with no ratings/reviews/affiliation fields), robots/sitemap consistency with the configured site URL (sitemap lists no hash fragments), the build copying every discovery file, and the share card staying a standard-size JPEG under 200 KB. A registry-deployment suite guards the live Preview deployment verification: the Koios transaction parser rejects hash mismatches, unconfirmed or invalid-contract records, and malformed block/epoch/timestamp fields, and the full check (run against a stubbed fetch) refuses to call the deployment verified when the upstream configuration drifts from the pinned script hash or protocol policy, or when Koios reports a different transaction. A transfer-sequence suite guards the Test step’s ledger model: exact `formatUnits` rendering past float precision, the issuer-funded starting ledger, denial knock-on effects (a blocked step moves nothing, later steps still evaluate, balances always sum to the designed supply), the per-transfer — not cumulative — cap, overspend failure on the balance left by earlier steps, pause/frozen paths, unrepresentable amounts on indivisible tokens, and the 1–12 step shape guard. A design-review suite guards the Design step's local audit: every template passes with no blockers, an invalid design reports a single blocker, a rule-less design warns it behaves like an ordinary native token, a cap equal to the supply warns it can never bind, cap shares are exact BigInt percentages (including the <0.01% case), the starts-paused and near-ceiling-supply warnings fire at their thresholds, the KYC-extended/allowlist mismatch and basic-KYC sender-only notes appear only when they apply, and the counts always sum to the findings. A sequence-builder suite guards the Test step's custom-sequence editing model: pure add / remove / reorder / update helpers that never mutate the list being edited, reject unknown accounts, non-string amounts, and unknown fields, hold the 1–12 step bounds (adding a thirteenth step and removing the last one both throw), and feed the simulator end to end — a step edited from a denial into a self-transfer applies, with final balances still summing exactly to the designed supply. An asset-fingerprint suite pins the CIP-14 implementation: all eight test vectors published in CIP-0014, BLAKE2b digests for empty, short, and multi-block inputs cross-checked against a reference implementation, hex-case canonicalisation, the empty-name and 32-byte-name boundaries, rejection of malformed policy ids and asset names, and the app-wiring guards for the live preview and the Koios cross-check (agreement, mismatch, and not-returned states, each with its honesty copy). A supply-sequence suite guards the chained issuance model (per-step authority and bounds against the running supply, blocked steps leaving the supply unchanged, burn-created ceiling headroom), and a supply-sequence-builder suite guards its custom editing model: pure add / remove / reorder / update helpers that never mutate the list being edited, reject unknown actions, actors, non-string amounts, and unknown fields, hold the 1–12 step bounds, and feed the simulator end to end — including a burn that only fits after the mints ahead of it have landed, and stays blocked when moved ahead of them. A timeline suite guards the combined issuance-and-transfer model: exact final state for a mint/distribute/burn lifecycle with the balances-always-sum-to-supply invariant checked on every scenario, the distributed-burn denial (blocked on the issuer's balance while the supply check passes), denial chains that change nothing, burn-all-then-re-mint restarts, the cap and the pause gating transfers but never issuance inside a timeline, the int64 ceiling binding mid-timeline, malformed steps reported as blocked steps rather than thrown timelines, and whole-token timelines at 0 decimals. A timeline-builder suite guards the combined lab's custom editing model: pure add / remove / reorder / update helpers for a mixed-kind list that never mutate the list being edited, reject unknown kinds, accounts, actions, actors, non-string amounts, and fields the step's kind does not carry, hold the 1–12 step bounds, convert a step when its kind is switched (amount kept, the new kind's defaults applied, no stale fields), feed the simulator end to end, and pin that the same burn and transfer land differently when their order is swapped. An eligibility-cohort suite guards the Midnight page's public-output preview: the default cohort isolates exactly one failing check per participant, cohort results match the single-participant model member for member, a requirement switched off admits exactly the participants it gated, boundary values (score equal to the minimum, age exactly 18) pass, malformed policies and cohorts throw instead of producing a partial public record, and the public output carries no private value under any key — a deep key scan plus a serialized-value scan both come back clean.
