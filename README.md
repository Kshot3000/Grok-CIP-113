# PRISM · Cardano programmable token studio

**Your asset. Your rules.** An open-source workspace for exploring CIP-113 programmable assets, real-world finance, and privacy-aware eligibility.

Built by **[KShot · @kshot9000](https://x.com/kshot9000)** for the Cardano community.

**[Open the website](https://kshot3000.github.io/Grok-CIP-113/)** · **[CIP-113 specification](https://github.com/cardano-foundation/CIPs/tree/master/CIP-0113)** · **[Report an issue](https://github.com/Kshot3000/Grok-CIP-113/issues)**

## What works

| Workspace | Functionality |
| --- | --- |
| Token studio | Eight editable templates — real-world asset, private credit, stablecoin concept, community access, carbon credit (indivisible tonnes, KYC-gated), event ticket (open access with a four-per-transfer anti-scalping cap), governance token (open access, issuer controls off so no issuer can pause or freeze voting power, and a per-transfer cap of exactly 1% of supply), and open payments (the catalog's only uncapped starting design: per-transfer limit off, open access, no issuer controls, so the whole supply can move in one modeled transfer — and the design review states the trade-off out loud, warning that with no rule active the design behaves like an ordinary native token) — validated token identity and precision, configurable allowlist / transfer cap / issuer controls / eligibility, and exact BigInt transfer modeling. The Test step also has a sequence lab: transfers run in order against a modeled ledger (the issuer starts holding the full designed supply), each step checked for sender balance, access, the per-transfer cap, issuer controls, and eligibility — a blocked step moves nothing and later steps are still evaluated, so the knock-on effect of a denial is visible in the final balances. A custom builder sits next to the presets: start from the preset you were viewing, then change senders, recipients, and amounts, add steps (up to 12), reorder them, or remove them, and run your own order against the same modeled ledger. |
| Substandard lab | Each template presets a CIP-113 Layer-3 substandard — freeze-and-seize, KYC, or KYC extended from the Foundation reference platform (community template uses PRISM’s generic rules). The Test step models the modules’ documented checks one by one: denylist on both parties, authorised-only seizure, the five sender-certificate checks, recipient allowlist membership and expiry, and the self-transfer exemption. Local simulation only; legacy design files without a substandard import as generic. A lifecycle panel runs transfers, denylist updates, and seizures in order against one modeled ledger and one evolving denylist — a holder listed mid-flight loses both transfer directions and becomes seizable, and removal restores transfers and ends the seizure authority again; only the module's own checks are modeled there, not the design's generic toggles. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds (switching a kind converts the step — an amount is kept where both kinds carry one, and a denylist update carries no amount), accounts, actors, and amounts, add transfer, denylist-update, or seizure steps (up to 12), reorder them, or remove them, and run your own lifecycle against the same model. The KYC-extended lab has its own lifecycle panel: transfers carrying a modeled certificate state (valid, missing, untrusted, invalid signature, naming another sender, or expired) run in order against one modeled ledger, one evolving recipient allowlist, and the module's global pause — an entry expiring mid-flight blocks the same transfer its renewal restores, a pause blocks every transfer whatever its certificate says, and each transfer is judged by the same checks as the single-shot lab, fed with the allowlist and pause as they stand at that step. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds, accounts, certificate states, entry states, and amounts, add steps (up to 12), reorder them, or remove them — switching a step's kind converts it to the new kind's defaults, and a removal carries no entry state, so its expired flag is dropped rather than carried into a later listing. The basic-KYC lab has its own lifecycle panel: transfers carrying a modeled certificate state (valid, missing, invalid signature, naming another sender, or expired) and naming the modeled entity that signed it run in order against one modeled ledger, one evolving trusted-entity list (KYC entity A starts trusted, entity B does not), and the module's global pause — an entity removed mid-flight leaves earlier transfers applied but its later certificates fail on the trusted-entity check alone, a second entity added mid-flight starts passing, and recipients are never checked, since basic KYC checks the sender only. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds, accounts, certificate states, signing entities, and amounts, add transfer, trust-update, or pause steps (up to 12), reorder them, or remove them — switching a step's kind converts it, keeping the modeled entity where both kinds name one (a transfer's signer becomes a trust update's subject, and back) and starting every other field from the new kind's defaults. |
| Supply lab | The Test step also models supply changes (issuance): the designed supply is an *initial* supply, so the lab runs a mint or a burn attempted by the issuer or by someone else, checked for issuance authority and for exact BigInt supply bounds — a mint may not pass the signed 64-bit asset ceiling (landing exactly on it is allowed, one base unit past it is blocked) and a burn may not exceed what was issued (burning the whole supply ends at exactly zero). The per-transfer cap is deliberately *not* applied: it gates transfers, not issuance. Labeled in the UI as PRISM's generic issuance model — not a Foundation substandard module, and a real token's issuance logic defines its own authority. No tokens are minted or burned. A supply sequence panel chains changes in order against a running modeled supply, so a burn creating int64-ceiling headroom a later mint can use (and a blocked change leaving the supply intact for later steps) is visible step by step; a custom builder sits next to its presets — start from the preset you were viewing, then change actions, actors, and amounts, add steps (up to 12), reorder them, or remove them, and run your own issuance schedule against the same model. A timeline lab then interleaves the two: transfer steps and supply steps run in one order against one modeled state — a ledger of balances plus the supply those balances always sum to — so minted tokens become transferable in the same timeline, and a burn draws on the issuer's modeled holding (tokens already distributed to other modeled accounts are not the issuer's to burn, so a burn can be blocked by the issuer's balance even when the total supply would cover it). Transfer rules gate only the transfer steps and issuance checks only the supply steps; a blocked step changes nothing and later steps still evaluate. A custom builder sits next to its presets — start from the preset you were viewing, then change step kinds (switching a kind converts the step, keeping its amount), senders, recipients, actions, actors, and amounts, add transfer or supply steps (up to 12), reorder them, or remove them, and run your own timeline against the same one-state model. |
| Learn CIP-113 | A ten-lesson plain-language learning path paraphrased from the official spec — why programmable tokens exist, shared-custody smart wallets, the withdraw-zero pattern, the registry, substandards, how a new token is created end to end (the shared infrastructure already deployed and never deployed by the creator, who need not know its hashes; the creator’s own transfer, third-party, and issuance scripts; an issuance minting policy parameterised by the minting-logic credential and the protocol parameters policy; registration refused for an already-registered policy or a wrong issuance minting policy; and new tokens enforced to the shared base address), third-party actions / unfracking, protocol upgradability (re-pointable wiring, the immovable base credential, and the two-phase nomination → promotion authority handover), and programmable tokens in DeFi and wallets (the integration duties, and why a protocol checks the substandard before accepting a token as collateral), and what a supporting wallet must do (balance queries and transaction history at the smart-wallet address, native transfers optional, issuance and third-party operations left to token-specific dApps, programmable-token identification by registry key, per-substandard user state, and the rule that a third-party key set is the substandard’s admin — never read off CIP-113 conformance alone) — each lesson naming its spec section. Plus a status tracker reproducing the spec’s frontmatter and its own “Path to Active” acceptance checklist verbatim (all four boxes unchecked while the status is Proposed), with the Foundation reference’s R&D / audit-pending caveat kept in place. Status snapshot re-verified against upstream on 2026-10-10. |
| Design review | The Design step ends with a live local review of the design's own coherence, recomputed on every edit: validation blockers, rule coverage (a design with no active rules warns it behaves like an ordinary native token), cap effectiveness (a cap equal to the whole supply warns it can never block a transfer; otherwise the cap's exact BigInt share of supply is shown), the pause state the design would start in, alignment between the generic toggles and the chosen substandard's documented checks (KYC extended expects a recipient allowlist; basic KYC checks the sender only), supply headroom against the signed 64-bit ceiling, and indivisibility at 0 decimals. Labeled in the UI as a local review — not a security audit, not validator review, and no guarantee a design is safe or deployable. |
| Design files | Local draft persistence, versioned JSON export, validated import, and developer handoff. Imports are integrity-verified: amounts must be exact decimal strings (JSON numbers are rejected outright — JSON parsing would round them past 2⁵³ and silently change the supply), the token summary must match the design field by field, the implementation section is cross-checked against the design too — its named substandard (id, name, reference, and modeled-locally flag), its Midnight mode (derived from the design's eligibility toggle), and its required developer-handoff steps must all match what PRISM exports, so a file edited to name a different module than the design models, misstate its eligibility plan, or drop the independent security review from its required steps is rejected — and a manifest claiming a deployed status, an Active CIP-113, a verified Midnight proof, a deployed bridge, or a RealFi affiliation/product is rejected instead of imported. Files whose status/implementation sections were hand-trimmed away still import (a design section that never stated a substandard still migrates to the generic module, its implementation copy uncross-checked); whitespace around names and amounts is canonicalised. A design file can also be verified without opening it: the Export step's Verify button runs exactly the import's checks and reports the design the file describes — identity, exact base-unit supply and limit, rule toggles, substandard, network, and whether an implementation section was present to cross-check — while your current design and saved draft stay untouched; the verifier returns no design to apply, so verifying can never become a quiet import, and a file that fails any check is refused whole. A design file can also be compared to the design currently open, without importing it: the Export step's Compare button runs the same verification, then reduces both designs through the verifier's own summary builder and reports every differing field — network, identity, exact base-unit supply and limit, rule toggles, starting pause state, template, and substandard (one field, not two) — in a fixed order, with the file's value and yours side by side; file metadata (the file's stated export time, whether an implementation section was present) is reported separately and never counts as a difference, two exports of the same design at different times compare as identical, and the comparison likewise returns no design to apply. No server account is required. |
| Sequence scenario files | The Sequence lab's scenarios are portable: a scenario exports as a deterministic JSON file carrying its modeled transfer steps only — no design, no balances, no run result — because its amounts are in the token units of the design it was written against, a design the file does not name (the same steps can apply under one design and be blocked under another). Handed files are read back with the design files' discipline: known modeled ledger accounts only, amounts as exact decimal strings (JSON numbers refused), no field a scenario never carries (a smuggled result, balance, or endpoint is refused by name), and a status claiming anything but the local simulation refused; hand-trimmed files may omit the status or note, but nothing present may contradict them. A handed file can also be verified without running it (the steps it describes, nothing applied) and compared step by step against the sequence open in the lab — position by position, in order, with a step present on only one side stated as such — and a file that fails any check is refused whole, never partially compared. Exporting, verifying, and comparing execute nothing: no validator runs, no balance is read, and no transaction is produced. |
| Supply-sequence scenario files | The Supply sequence lab's scenarios are portable the same way: a supply scenario exports as a deterministic JSON file carrying its modeled supply changes only — no design, no starting or resulting supply, no run result — because its amounts are in the token units of the design it was written against, a design the file does not name (the same steps can apply under one design and be blocked under another: a burn that fits a large designed supply exceeds a smaller one). Handed files are read back with the same discipline: a mint or a burn attempted by the modeled issuer or by someone else only, amounts as exact decimal strings (JSON numbers refused), no field a supply scenario never carries (a smuggled result, supply, or endpoint is refused by name), and a status claiming anything but the local simulation refused; hand-trimmed files may omit the status or note, but nothing present may contradict them. A handed file can also be verified without running it (the steps it describes, nothing applied) and compared step by step against the supply sequence open in the lab — position by position, in order, with a step present on only one side stated as such — and a file that fails any check is refused whole, never partially compared. Exporting, verifying, and comparing execute nothing: nothing is minted or burned, no supply is read, and no transaction is produced. |
| Timeline scenario files | The Timeline lab's scenarios are portable the same way: a timeline scenario exports as a deterministic JSON file carrying its modeled steps only — no design, no starting or resulting supply, no balances, no run result — because its amounts are in the token units of the design it was written against, a design the file does not name (the same steps can apply under one design and be blocked under another: a burn that fits while the issuer still holds the tokens is blocked once they are distributed). One thing this format carries that the single-kind formats do not is the kind of every step: a step is a transfer or a supply change by what it says, and each step names only its own kind's fields — a transfer step never carries an action, a supply step never carries a sender — so a field belonging to the other kind is refused by name. Handed files are read back with the same discipline: each step a transfer between known modeled accounts or a mint or a burn attempted by the modeled issuer or by someone else, amounts as exact decimal strings (JSON numbers refused), no field a timeline scenario never carries (a smuggled result, supply, balances, or endpoint is refused by name), and a status claiming anything but the local simulation refused; hand-trimmed files may omit the status or note, but nothing present may contradict them. A handed file can also be verified without running it (the steps it describes, both kinds counted, nothing applied) and compared step by step against the timeline open in the lab — position by position, in order, a step whose kind differs differing whatever its amount says, and a step present on only one side stated as such — and a file that fails any check is refused whole, never partially compared. Exporting, verifying, and comparing execute nothing: nothing is transferred, minted, or burned, no state is read, and no transaction is produced. |
| Registry entry preview | The Export step also renders a deterministic, application-specific preview of the design information a CIP-113 registry entry would need to describe — token identity, exact BigInt base units, transfer policy, and substandard — alongside an explicit list of what only a real deployment can supply (policy ID, registry node position and proofs, Plutus Data / CBOR encoding). Labeled “NOT A CIP DATUM” in the UI; PRISM registers nothing. A preview file you were handed can be verified in the same step: its honesty flags (application-specific, not a CIP datum, not registered) must state exactly what a preview is, amounts must be canonical exact decimal strings (a JSON number or a padded string is rejected, never converted) with a per-transfer limit no larger than the supply, the substandard section must match PRISM’s catalog field by field, the still-required list and note must match the canonical text when present, and any field a preview never carries — a policy ID, a CBOR encoding, a datum hash — is refused outright. Hand-trimmed files may omit the flags, list, or note (absent is tolerated, contradicting is rejected); the verifier returns the canonical preview and, like the manifest importer, verifies only the file’s internal consistency — it imports nothing, registers nothing, and changes no design. A handed preview can also be compared to the open design’s preview in the same step: comparison runs the verifier first (a file that fails verification is refused whole, never partially compared), then reports differences across ten fields in a fixed order — network, token name, ticker, decimals, initial supply in exact base units (compared bit-for-bit past 2^53), transfer access, per-transfer limit (null when no limit is set), issuer-pause and eligibility modeling, and the substandard as one field. The honesty flags, still-required list, and note are verified rather than compared — the verifier canonicalises them, so a hand-trimmed file omitting them compares as identical to its own full export — and the return carries the two canonical previews and the differences only, no design object, so comparing cannot become a quiet import either. |
| Cardano wallets | Real CIP-30 discovery and permission flow, network checks that name the expected network (CIP-30 reports only mainnet vs testnet, so Preview vs Preprod is confirmed in the wallet), rejection of malformed network ids and incomplete wallet APIs, public payment address, account-change detection, and app disconnection. On connect, an address book is also read locally from the wallet's optional CIP-30 lists (used / unused / reward addresses): every entry is decoded in the browser, counted by kind, checked against the connected network (mismatches flagged, never hidden), matched against the CIP-113 smart-wallet shape with the usual shape-is-not-membership caveat, and the reward (stake) credential is compared with the payment addresses' stake credential. A list a wallet does not offer is shown as unavailable, never guessed; no balance is read. Read only. |
| Network explorer | Live Koios chain tip and native asset lookup, refresh and failure states, no invented metrics. The registry panel can also verify the Foundation’s pinned Preview reference deployment live: the platform repository’s configuration is fetched fresh and must match the pinned script hash and protocol policy field by field, and Koios Preview must confirm that exact deployment transaction in a block with valid contract execution, before anything is shown as confirmed. Registry browsing reads the Foundation’s hosted programmable-tokens indexer for the selected network (preview-/preprod-/mainnet-indexer.programmabletokens.xyz — the platform’s own indexer family, verified live on 2026-10-10): strictly parsed deployment records (protocol parameters ID, registry node policy, programmable-logic hash, indexed token count, slot, deployment transaction), with the Preview record cross-checked against the pinned reference deployment — the pinned bootstrap transaction must be listed and its programmable-logic hash must equal the pinned script hash before the panel calls it that deployment, and a mismatch or absence is reported, never smoothed over. Counts are that indexer’s view of its own deployment, not a universal token census, and an unreachable indexer renders an explicit unavailable state instead of stale or invented numbers. |
| CIP-113 version (spec-listed) | The registry panel also names the CIP-113 version the specification itself lists: the spec defines a CIP-113 version as the hash of the bootstrap transaction that initialised a deployment, and its CIP-113 Version table lists exactly one network — Preview, bootstrap transaction `61fae36e28a62a65496907c9660da9cf5d27fa0e9054a04581e1d8a087fbd93e`. That transaction is a different transaction from the Foundation platform reference deployment pinned in the same panel (`8e9668a6…`, the deployment the hosted indexers index): each bootstrap hash identifies the deployment it initialised, so the two records must not be conflated, and neither makes the other wrong. A local classifier (`classifyBootstrapTx`) names a claimed bootstrap hash as the spec-listed version, the platform reference deployment, or neither pinned record — 'neither' says only that PRISM pins no record for it — and the panel verifies the spec-listed transaction live against Koios Preview, judged by the same deployment parser as the platform check, before anything is shown as confirmed. The spec table lists no version for Preprod or Mainnet, so none is shown for them. |
| Registered tokens (live) | The same registry read also fetches the deployment’s registered token nodes from the indexer’s `GET /api/v1/registry/tokens` endpoint — the actual CIP-113 registry chain, one node per registered token, its key the token’s policy ID. The response is parsed strictly (protocol parameters, then every node: 28-byte key, a next that is either the following 28-byte key or the 30-byte terminal sentinel, and the minting / transfer / third-party / unfracking logic scripts and global-state policy, each a 28-byte hash or empty — empty is a meaning, not a defect: an empty unfracking script forbids unfracking for that policy, an empty global-state policy expects no global-state reference input). Before the list is shown as a registry, PRISM verifies it as a chain and cross-checks it against the deployments list in the same panel: keys strictly ascending, every node’s next pointing at the following key, the last node terminating at the sentinel, and the deployments endpoint agreeing on the registry node policy, the programmable-logic hash, and the indexed token count — two indexer endpoints that must agree, with any disagreement named and the list flagged do-not-rely instead of smoothed over. The origin node is not part of this endpoint’s response, and a failed tokens read renders its own explicit unavailable state while the deployments above it stand on their own read. Verified live on 2026-10-10 against all three networks (Preview 5 nodes, Preprod 16, Mainnet 3 — every chain check passing). This is the indexer’s view of the chain, chain-checked locally — not an on-chain UTxO verification, and PRISM registers nothing. |
| Full registry walk (live) | The registry read also walks each deployment's whole chain from its head, via the indexer's `GET /api/v1/registry/nodes/all?protocolParamsId=<id>` endpoint — keyed by the numeric protocol parameters ID that only the deployments endpoint reports (a wrong ID returns an empty-looking walk, so an unusable ID is refused before any fetch). Unlike the tokens endpoint, this response includes the origin node: the empty-key head of the registry, carrying no logic of its own. The response is parsed strictly (an origin carrying any logic, an empty key anywhere but the head, a group with no origin to walk from, or any malformed node refuses the whole response), and the walk is then verified, not just displayed: the origin must carry no logic and its `next` must name the first token — or the terminal sentinel directly, for an empty registry, whose origin-only terminating walk is verified as a complete walk of an empty registry — the token nodes must pass the same chain check as the tokens read, the deployments list must agree on policy, logic hash, and count, and the walk must agree with the registered-tokens read node for node, every field — two reads of one chain that disagree anywhere fail the walk with the disagreement named. When the tokens read itself failed, the agreement is reported as not compared, never as passed. A failed walk read renders its own explicit unavailable state while the deployments and tokens above it stand on their own reads. Verified live on 2026-10-10 against all three networks (Preview 6 nodes including the origin, Preprod 17, Mainnet 4 — every walk check passing). This is the indexer's view of the chain, walk-checked locally — not an on-chain UTxO verification, and PRISM registers nothing. |
| Single-token registry lookup (live) | The registry panel also looks up ONE token by its policy ID, via the indexer's own single-token endpoints — `GET /api/v1/registry/is-registered/{policyId}` first, and only when that answer says registered, `GET /api/v1/registry/token/{policyId}` for the token's node on its own (an unregistered policy makes no second call: that endpoint answers it with an empty 404, the same fact stated worse). Both answers are parsed strictly — the registration answer must be a real boolean under its named field, never a coerced truthy value, and the node is judged by the same registry-node parser as the tokens and walk reads, with the origin shape refused and the returned node's key required to be the policy that was asked for, so a node answering to a different policy is refused, not displayed. The lookup is then cross-checked against the registered-tokens read: the registration answer and the tokens list must agree on whether the policy is registered, and a registered node must agree with its node in that list field for field — any disagreement fails the lookup by name. When the tokens read itself failed, the cross-check is reported as not compared, never as passed. An unregistered answer is stated as this indexer's view of its own deployment — a policy it lists no node for — never as proof that no such token exists anywhere, and a failed lookup renders its own explicit unavailable state. Verified live on 2026-10-16 against Preview (its first registered token looked up and cross-checked; the all-zero policy answered not registered). Read-only — PRISM registers nothing. |
| Protocol parameter versions (live) | The registry read also reads the indexer's `GET /api/v1/protocol-params/versions` endpoint — every version of the protocol parameters the deployment has run under, with the transaction that deployed it, its slot and time, and which version stands as the default now: the live history behind the upgrades the protocol-upgrade model plans locally. The response is parsed strictly (the default flag must be a real boolean; a malformed record refuses the whole response), and the history is then verified, not just displayed: exactly one version must stand as the default (zero leaves nothing standing, two leaves it ambiguous), no deployment transaction may be listed twice, the list must run in slot order, and the standing default must agree with the deployments list above on the registry node policy, the programmable-logic hash, the deployment transaction, and the slot — two endpoints that must agree on the version both call current. When no deployments list is available to compare, the agreement is reported as not compared, never as passed; an empty history verifies nothing. A failed versions read renders its own explicit unavailable state while the deployments, tokens, and walks above it stand on their own reads. Verified live on 2026-10-10 against all three networks (one standing version each, every check passing, each default agreeing with its deployments record field for field). This is the indexer's record of the deployment's parameter history — not an on-chain verification, and PRISM registers nothing. |
| Latest protocol parameters (live) | The registry read also reads the indexer's `GET /api/v1/protocol-params/latest` endpoint — the protocol parameters standing NOW, with the full credential set the deployments list never carries: the transfer, third-party, programmable-logic-global, issuance-logic, unfracking, and upgrade credentials, the credential nominated for a pending upgrade (shown as a stated absence — no pending upgrade nominated — when the indexer reports none), and the inline-datum size limit. When no deployments list is available to compare, the agreement is reported as not compared, never as passed. | Sorted registered tokens (live) | The registry read also reads the indexer's `GET /api/v1/registry/tokens/sorted?protocolParamsId=<id>` endpoint — one deployment's registered token nodes alone, in the order the endpoint's name claims. | Substandard modules (live) | The registry read also reads the indexer's `GET /api/v1/modules` endpoint — the platform's Layer-3 substandard module catalogue for the network (Dummy, Freeze-and-seize, and the RWA Token profile today): the platform's Layer-3 modules as its indexer catalogues them — a list that does not line up one-for-one with the modules the Substandard lab models locally (see the coverage row below). The response is parsed strictly (module ID, name, description, and a non-empty validator list; every entry a title, even-length hex script bytes, and a 28-byte stated script hash), and then PRISM does the one thing an indexer listing alone cannot do for itself: it recomputes every validator's script hash in the browser — Blake2b-224 of the Plutus V3 language tag (0x03) and the entry's own script bytes, the ledger's script-hash construction — and the catalogue is shown as verified only when every recomputed hash equals the stated hash, module IDs are unique, and validator titles are unique within each module (the handlers of one compiled validator share one script, so entries are grouped by script: 40 entries, 16 distinct scripts today). | Substandard module coverage (live) | The same registry read accounts for the live catalogue against the studio's local substandard models with `moduleCoverageCheck`, because the two lists do not line up one-for-one and the panel must not imply they do. The one exact correspondence is the indexer's `freeze-and-seize`, modeled locally as `freeze-seize` (the studio shortens the module's name in design files; it is the same Foundation module). `dummy` is the platform's test module, catalogued with no local model by design. `rwa-token` is a profile, not one of the studio's modules: it has no single local model — its own description names KYC-gated transfers, denylisting, and seizures, which PRISM models separately in its Freeze-and-seize, KYC, and KYC extended models, so those are recorded as related to the profile, and modeling parts of a profile is never presented as modeling the profile. On the local side, KYC and KYC extended have no catalogued module of their own (they are documented platform modules the indexer does not catalogue as separate entries) and PRISM's generic rules are its own design aid with no platform counterpart. The check passes when every catalogued module is classified; a catalogued module PRISM has not classified fails the check by name, so a new module appearing in the catalogue can never silently pass as modeled. An empty catalogue accounts for nothing. Every module row in the panel carries its own model line (studio model, no studio model, or no single studio model). Verified live on 2026-10-10 against all three networks: 1 of 3 catalogued modules modeled exactly, on every network. |
| Registry proof planner | The registry panel also plans CIP-113 registry proofs locally against a modeled registry list you supply: for each distinct policy a transfer would touch, in lexicographic order, it names the proof the spec requires — the policy's own registry node as a TokenExists proof when the policy is in the list, or the covering node as a TokenDoesNotExist proof when it is not (the node whose key is the largest key below the policy and whose `next` is above it, after which the asset is treated as an ordinary native token). The modeled list is validated as the on-chain list is built — every key exactly 28 bytes, each key once, strictly increasing — and a list breaking those invariants is refused rather than silently sorted. The UI states the plan proves a policy's status only against the modeled list — PRISM reads no live registry here. | Reserve holdback model | A NEW axis — money HELD BACK from a settlement, still the seller's: a payment tool or marketplace settling a sale holds a stated share of the seller's settlement back as a rolling reserve against later refunds and chargebacks, stated exactly in BigInt: the held amount is floor(settlement x reserve rate / 10,000), measured against THE GROSS SETTLEMENT AMOUNT — never against what remains after the holdback itself, which is circular and understates it (on the preload, 1,000 at a stated 10% holds 100, where 10% of the 900 paid at once states 90). A reserve is NOT a fee — a fee is kept, a reserve is held and remains the seller's — and NOT escrow, which holds a buyer's payment before delivery. The held amount is floored to the base unit and what is paid at once is what remains, so held plus paid at once is the settlement exactly. A reserve rate of zero states NO HOLDBACK — the settlement is paid whole at once, an outcome, not a missing input — a stated rate that floors to zero on a small settlement holds nothing at that size, stated as such, a rate of the whole holds the settlement whole and pays nothing at once, stated as such, and a rate beyond the whole is refused. LOCAL MODEL — PRISM holds nothing, settles no sale, and pays no seller; a real design must disclose its gross settlement amount, its stated reserve rate and that the reserve is measured against the gross settlement and floored to the base unit, that the held amount remains the seller's and is not a fee, how long it is held and when it is released, and what claims may be taken from it, before the first settlement is held back. |
| Reserve release model | The reserve axis's second moment — a reserve is held to be RELEASED: when the hold ends, stated claims (refunds, chargebacks, fees owed under the design's own terms) are taken from what was held and the remainder goes to the seller, stated exactly in BigInt: the released amount is the held amount minus the claims taken, measured against THE AMOUNT HELD — never against the gross settlement minus claims, which hands what was already paid at once back a second time (on the preload, a 1,000 settlement at a stated 10% holds 100; claims of 25 taken from it release 75, where the settlement measure states 975). Claims taken plus released is the held amount exactly, and claims plus released plus what was paid at once is the settlement exactly. Claims beyond what is held are REFUSED, never capped at the held amount — a claim larger than the reserve is not met from this reserve. Claims of zero release the held amount whole, stated as such; claims equal to the whole held amount release nothing, stated as such; where nothing is held there is nothing to release. LOCAL MODEL — PRISM holds nothing, releases nothing, and pays no seller; a real design must disclose its held amount, what claims may be taken from it and in what order, that claims beyond the held amount are not met from the reserve, and that the remainder released is the seller's own money, before the first reserve is released. |
| Indexation model | A NEW axis — a stated amount INDEXED at a stated rate per period for stated periods (an inflation-linked price, an indexed payout, a rent-like stream), stated exactly in BigInt as an exact rational: the per-period factor (10,000 + rate) / 10,000 is raised to the stated periods and the adjusted amount is floored ONCE, at the end — flooring per period discards fractions later periods compound on and understates the amount (999 base units at 250 bps for two periods state 1,049 exactly, 1,048 floored per period). The adjustment COMPOUNDS, never simple: a simple adjustment prices every period on the original amount and understates a rise (1,000 at 250 bps for three periods states 1,076.890625 compounded, 1,075 simple) and overstates a fall (at −1,000 bps for two periods the amount falls to 810 compounded, 800 simple). Adjusted x denominator + remainder is amount x numerator exactly. A rate of zero or zero periods states NO INDEXATION; an increase below one whole base unit at this size leaves the amount unchanged, flagged; a rate at or beyond −10,000 bps is refused, as is one beyond 10,000 bps per period. Which index the rate follows, any cap or floor on the rate, and tax on the adjustment are NOT priced. LOCAL MODEL — PRISM indexes nothing, moves no amount, and pays no one; a real design must disclose its stated rate and that it compounds, that the exact factor is floored once at the end, which index the rate follows, and any cap or floor on the rate, before the first amount is indexed. |
| Indexation position model | The indexation model's second moment — an indexed amount met PART WAY THROUGH its periods: some have elapsed and it stands at an intermediate amount, with the remaining periods still to run. Composes the indexation model unchanged twice, BOTH measured from the ORIGINAL amount: current is the amount after the elapsed periods, final is the amount after all periods, and the remaining adjustment is final minus current (elapsed + remaining is the total adjustment exactly; current + remaining is final exactly). The final amount is NEVER stated by re-compounding the floored current amount — that loses the fraction the first floor left and prices the elapsed periods twice (999 base units at 250 bps, 1 of 2 periods elapsed, state a current 1,023 and a final 1,049, where re-compounding the floored 1,023 states 1,048). Elapsed periods beyond the total are refused, never capped; no periods elapsed states the position at its start; all elapsed states it COMPLETE; a rate of zero states no indexation at any point. A future change in the stated rate, which index the rate follows, any cap or floor on the rate, and tax on the adjustment are NOT priced. LOCAL MODEL — PRISM indexes nothing, moves no amount, and pays no one; a real design must disclose its stated rate, that a part-way amount and its final amount are both measured from the original amount, and that a future rate change is a new statement, before the first amount is indexed. |
| Withholding model | A NEW axis — a stated share of a GROSS payment withheld by the payer and remitted to a stated authority ON THE RECIPIENT'S BEHALF, stated exactly in BigInt: the withheld amount is floor(gross payment x withholding rate / 10,000), measured against THE GROSS PAYMENT — never against what the recipient receives, which is circular and understates it (on the preload, a 1,000 payment at a stated 20% withholds 200 and pays 800 over, where 20% of the 800 paid over states 160). The withheld amount remains the recipient's, remitted in their name: it is NOT a fee (a fee is kept by whoever charges it) and NOT a reserve (a reserve is held for later release to the same person; withheld money is remitted onward, not released back). Withheld + paid over is the gross payment exactly. A rate of zero states no withholding; a rate flooring to zero on a small payment withholds nothing at that size; a rate of the whole withholds the payment whole, stated; a rate beyond the whole is refused. Which authority and jurisdiction, whether the recipient's own status changes the rate, remittance timing, any credit for over-withholding, and any gross-up are NOT priced. Local model only — PRISM withholds and remits nothing; a real design must disclose the gross payment, the stated rate measured against it, that the withheld amount remains the recipient's and where it is remitted, and that it is floored to the base unit, before the first payment is made under it. |
| Withholding credit model | The withholding model's second moment — a stated CREDIT for amounts already withheld on earlier payments, applied against a LATER payment's withholding. Composes the withholding model unchanged: the withholding DUE is measured against THE FULL GROSS PAYMENT first, the credit is then applied against that due (applied is the smaller of the credit stated and the due), and only the remainder of the due is withheld in cash — cash withheld + credit applied is the due exactly, and cash withheld + paid over is the gross payment exactly. The credit is NEVER netted off the gross payment before the withholding is measured: netting first understates the due (on the preload, a 1,000 payment at a stated 20% owes 200 of withholding; netting a stated 50 credit off first states a due of 190 on the remaining 950, the difference being exactly the stated rate taken on the credit itself) and consumes the credit against money that was never withheld. An applied credit is NOT a cash payment (no money moves — it stands in for cash withholding, so the amount remitted on the recipient's behalf across the payment is the due exactly) and NOT a refund: credit beyond the due is never paid out — what is paid over never exceeds the gross payment — it remains a stated credit balance, carried onward. A credit of zero states no credit (the withholding stands exactly as the withholding model states it); a credit equal to the due covers the withholding whole (nothing withheld in cash, paid over whole, stated); where no withholding is due (no rate stated, or a rate flooring to zero at this size) the whole credit remains, stated. Where the credit came from, whether it is valid or accepted, whether it expires or is capped, what happens to a credit balance that remains, and any gross-up are NOT priced. Local model only — PRISM withholds, remits, and credits nothing; a real design must disclose the gross payment and stated rate, the credit stated and where it came from, that the credit is applied against the due and never netted off the payment first, that credit beyond the due is not paid out, and what happens to a remaining credit balance, before the first payment is made under it. |
| Cashback model | A NEW axis — the buyer pays the FULL purchase amount first and a stated share of it comes back afterwards. The cashback is floor(purchase x rate / 10,000), measured against THE FULL PURCHASE AMOUNT — measuring it against the buyer's net cost (purchase minus cashback) is circular and understates it (on the preload, a 1,000 purchase at a stated 5% returns 50 and leaves a net cost of 950, where 5% of the 950 net states 47). A cashback is NOT a discount: a discount reduces what the buyer PAYS before payment, while a cashback buyer pays the whole purchase at the point of sale (amount paid at purchase is the purchase exactly) and the net cost is the outcome of two movements. Identity: cashback + net cost === purchase exactly. A rate of zero states no cashback; a rate flooring to zero on a one-base-unit purchase returns nothing at that size; a rate of the whole returns the purchase whole, stated (net cost zero — the buyer still paid it whole first); a rate beyond the whole is refused. Eligibility, any cap, when the cashback is paid and in what asset, who funds it, whether a later refund claws it back, and tax are NOT priced. Local model only — PRISM pays no cashback, sells nothing, and returns nothing; a real design must disclose the full purchase and stated rate, that the buyer pays in full first, who funds the cashback and when it is paid, any cap or eligibility rule, and whether a refund claws it back, before the first purchase is made under it. |
| Cashback clawback model | The cashback axis's second moment — the cashback model states a share of a purchase paid in full coming back afterwards and leaves whether a later refund claws it back unpriced; a refund is that later moment. Composes the cashback model unchanged and states the clawback exactly in BigInt: clawback is floor(cashback actually returned x refund / purchase) — the PRO-RATA share of THE CASHBACK ITSELF. It is NEVER recomputed as the stated rate taken on the refund amount: the cashback was floored when stated, so recomputing prices a return never made (decimals 0: a 999 purchase at 5% returns 49; a 500 refund's pro-rata clawback is 24, where the rate on the refund states 25). Identities: clawback + retained cashback === cashback exactly; refund + kept purchase === purchase exactly. A refund of zero states no clawback and the cashback stands whole; a refund of the whole purchase claws the cashback back whole (retained zero, net cost zero); a refund beyond the purchase is refused. Where no cashback was returned there is nothing to claw back, stated. The clawback is NOT a fee and NOT a penalty: it never exceeds the cashback actually returned. Whether the refund is due, its timing, and how a clawback is recovered from a buyer who already spent the cashback are NOT priced. Local model only — PRISM refunds nothing and claws nothing back; a real design must disclose whether a refund claws its cashback back and on what share, before the first purchase is made under it. |
| Stored-value payment model | A NEW axis — the buyer pays with value they already hold: a stated stored-value balance (gift card / prepaid balance) applied to a purchase. | Stored-value top-up model | The stored-value axis's second moment — the payment model applies a stated balance to a purchase and leaves how the balance was loaded unpriced; a load is that earlier and later moment. Local model only — PRISM writes no forward, holds no margin, closes out nothing, and settles nothing. |
| Call option settlement model | A NEW axis — the forward models oblige BOTH sides, but two parties can also agree a contract that obliges only ONE side, priced nowhere before. A call option gives its holder the RIGHT, not the obligation, to buy a stated quantity at a stated strike price; the holder pays a stated premium per unit upfront for that right — stated here, never derived (no volatility or time-value calculation). States the settlement at expiry exactly in BigInt: the payoff per unit is the part of the settlement price ABOVE the strike, floored at zero, measured against THE TWO PRICES ACTUALLY STATED, multiplied by THE QUANTITY ACTUALLY STATED (on the preload, 10 units, strike 100, settling at 125, premium 5 per unit, state a 25 per-unit payoff, a 250 payoff, a 50 total premium, and a 200 holder net). The payoff is measured on the part above the strike, never on the settlement price alone, which would pay the whole settlement value as if the strike had never been promised. The settlement is ASYMMETRIC: at or below the strike the option expires worthless, the payoff is zero, and the holder loses the whole premium and no more, however far the price falls. The break-even settlement price is the strike plus the premium per unit; counting the premium, holder net + writer net === 0 exactly. The payoff is NOT a fee and the premium is NOT a fee. Cash settlement at expiry only: delivery, early exercise, premium derivation, margin, default, and fees are NOT priced. Local model only — PRISM writes no option, holds no margin, and settles nothing. |
| Put option settlement model | The option axis's mirror contract — the call model states the right to BUY at a strike; a put option gives its holder the RIGHT, not the obligation, to SELL a stated quantity at a stated strike price, priced nowhere before. The holder pays a stated premium per unit upfront for that right — stated here, never derived (no volatility or time-value calculation). States the settlement at expiry exactly in BigInt: the payoff per unit is the part of the strike ABOVE the settlement price, floored at zero, measured against THE TWO PRICES ACTUALLY STATED, multiplied by THE QUANTITY ACTUALLY STATED (on the preload, 10 units, strike 100, settling at 75, premium 5 per unit, state a 25 per-unit payoff, a 250 payoff, a 50 total premium, and a 200 holder net). The payoff is measured on the part below the strike, never on the strike price alone, which would pay the whole strike value as if the settlement price had been zero. The settlement is ASYMMETRIC: at or above the strike the option expires worthless, the payoff is zero, and the holder loses the whole premium and no more, however far the price rises; and the payoff is CAPPED at the strike value, because a settlement price cannot fall below zero. The break-even settlement price is the strike minus the premium per unit; counting the premium, holder net + writer net === 0 exactly. The payoff is NOT a fee and the premium is NOT a fee. Cash settlement at expiry only: delivery, early exercise, premium derivation, margin, default, and fees are NOT priced. Local model only — PRISM writes no option, holds no margin, and settles nothing. |
| Option sale before expiry model | The option axis's second moment — the settlement models state what a call or a put pays AT expiry and leave disposal before expiry unpriced. A holder can sell the right itself to a buyer before expiry at a stated sale price per unit, stated exactly in BigInt: the proceeds are the sale price per unit multiplied by THE QUANTITY ACTUALLY STATED, and the seller's completed result is the proceeds minus the whole premium ACTUALLY PAID (on the preload, 10 units whose holder paid a premium of 5 per unit, sold at 8 per unit, state proceeds of 80, a premium total of 50, and a seller net of 30). The break-even sale price per unit is the premium per unit itself. The sale price is STATED, never derived (no intrinsic-value, volatility, or time-value calculation). The proceeds are NOT the expiry payoff (no strike and no settlement price enter the model) and NOT a fee; the premium is NOT a fee. The sale EXTINGUISHES the seller's position: no expiry payoff remains for the seller at any settlement price, and no later price reopens or reprices the result — including a sale at zero, which gives the right away, still closes the position, and loses the whole premium. The seller's loss is floored at the premium, because proceeds can never be negative. The buyer's result (open, depending on an expiry that has not happened) and the writer's position (not closed by the sale) are NOT priced. Transfer rules, default, fees, and taxes are NOT priced. Local model only — PRISM writes no option, runs no market, and transfers no right. |
| Loan guarantee model | A new axis — every earlier model states what the parties to a contract pay each other; a guarantee brings in a third party who pays when the borrower does not. A lender is owed a stated obligation, the borrower has paid part of it, and a guarantor has promised to pay the lender the part the borrower leaves unpaid, up to a stated guarantee cap, stated exactly in BigInt: the shortfall is THE OBLIGATION ACTUALLY STATED minus THE AMOUNT THE BORROWER ACTUALLY PAID, and the guarantor pays the smaller of that shortfall and THE CAP ACTUALLY STATED (on the preload, an obligation of 1,000 on which the borrower paid 600, under a cap of 500, states a shortfall of 400 the guarantor pays whole, and the lender receives 1,000 in all). The payment is measured on the shortfall, never on the whole obligation, which would charge the cap against money the borrower already paid. The guarantor's payment does NOT extinguish the debt: the borrower now owes the guarantor the amount the guarantor paid, and still owes the lender any shortfall the cap did not reach, so the shortfall is conserved exactly — a guarantee moves a debt, it does not forgive one. A borrower who paid the whole obligation states no shortfall: the guarantee is not called and the guarantor pays nothing. A payment above the obligation is refused. The payment is NOT a fee, and any fee for the guarantee itself is NOT priced. Interest separation, default determination, guarantor solvency, collateral, reimbursement collection, fees, and taxes are NOT priced. Local model only — PRISM lends nothing, guarantees nothing, and pays no lender. |
| Holder distribution model | What a pool — an airdrop, a revenue share, a reward pool — pays each holder when it is divided by HOLDINGS, priced pro-rata: each holder receives floor(pool × balance ÷ total balances), so their share is derived from their balance, never entered, unlike the revenue split, which divides by entered percentage shares. Per-holder flooring leaves an undistributed remainder that belongs to no holder (distributed + undistributed always equals the pool, and the remainder is always less than the holder count in base units); a zero-balance holder receives zero, and one holder holding the whole total balance receives the whole pool exactly. Each holding share is derived from the BigInt balance amounts, never from the floored receives. Local model only — PRISM distributes nothing, holds no pool, pays no holder; a real design must disclose the snapshot of balances a distribution is priced on and what happens to the undistributed remainder, exactly as modeled. |
| Capped holder distribution model | What a pool pays each holder when the pro-rata division by holdings carries a PER-HOLDER CAP: a holder whose share passes the cap receives only the cap, and what they did not take is divided again among the holders still under it, round by round (water-filling), until nobody left can take more or nothing is left but floor dust. No holder ever receives more than the cap, and distributed + undistributed always equals the pool — but when every holder with a balance is at the cap, the undistributed remainder is cap-blocked, not floor dust: it is not bounded by the holder count and can be most of the pool. Each holding share is still derived from the BigInt balance amounts, never from the capped receives. Local model only — PRISM distributes nothing, holds no pool, pays no holder, and enforces no cap; a real design must disclose its cap, the snapshot of balances a distribution is priced on, and what happens to any remainder the cap leaves undistributed, exactly as modeled. |
| Minimum-guarantee holder distribution model | What a pool pays each holder when the pro-rata division by holdings carries a PER-HOLDER MINIMUM GUARANTEE: the minimum times the eligible holder count is reserved from the pool first, and what remains is divided pro-rata by holdings, so each eligible holder receives the minimum plus their remainder share. The guarantees are feasible only if the minimum times the eligible count fits in the pool, and only holders who actually hold are eligible — a zero-balance holder receives zero and is guaranteed nothing. A minimum of zero reproduces the uncapped division exactly. Distributed + undistributed always equals the pool, and the undistributed remainder is floor dust from the remainder division only (less than the eligible holder count in base units). Each holding share is still derived from the BigInt balance amounts, never from the receives. Local model only — PRISM distributes nothing, holds no pool, pays no holder, and guarantees nothing; a real design must disclose its minimum, who is eligible for it, the snapshot of balances it is priced on, and what happens to the undistributed remainder, exactly as modeled. |
| Capped-and-floored holder distribution model | What a pool pays each holder when the pro-rata division by holdings carries BOTH a PER-HOLDER MINIMUM GUARANTEE and a PER-HOLDER CAP: the minimum times the eligible holder count is reserved from the pool first, and what remains is divided pro-rata by holdings in rounds under each holder's cap room — the cap minus the minimum, because the minimum is already part of what they receive — so every eligible holder receives at least the minimum and at most the cap. The bounds interact: a cap below the minimum is contradictory and refused, a minimum of zero reproduces the capped model, a cap no remainder share can reach reproduces the minimum-guarantee model, and a cap equal to the minimum pays exactly the minimum and leaves the whole remainder cap-blocked. Distributed + undistributed always equals the pool; the remainder is floor dust unless every eligible holder is at the cap, when it is cap-blocked and can be most of the pool. Each holding share is still derived from the BigInt balance amounts, never from the receives. Local model only — PRISM distributes nothing, holds no pool, pays no holder, guarantees nothing, and enforces no cap; a real design must disclose its minimum, its cap, who is eligible for the guarantee, the snapshot of balances it is priced on, and what happens to any remainder the cap leaves undistributed, exactly as modeled. |
| Holder distribution claim-window model | What a priced distribution looks like AFTER ITS CLAIM DEADLINE: the pro-rata allocation by holdings is priced exactly as the holder distribution model prices it, and each holder's allocation then splits by claim status — a holder who claimed is paid out their whole allocation, a holder who did not claim leaves their whole allocation unclaimed, a stated claim status must be a boolean (claimed or unclaimed) or it is refused, and a missing status means unclaimed. Claimed + unclaimed always equals the amount distributed, and claimed + unclaimed + the undistributed floor dust always equals the pool. The claimed share is derived from the BigInt amounts claimed, never from how many holders claimed; only holders with an allocation count toward all-claimed, so a zero-allocation holder's status changes nothing, and when nothing was distributed nothing was there to claim. Local model only — PRISM distributes nothing, holds no pool, pays no claim, and runs no claim window; a real design must disclose its claim deadline, what counts as a claim, and where unclaimed allocations go (treasury, redistribution, burn, or a later window) — PRISM models the amount, the design chooses the destination, exactly as modeled. |
| Holder distribution redistribution model | One destination for the UNCLAIMED allocations the claim-window model states, priced end to end: the claim-window model is composed unchanged, and its unclaimed total becomes a second pool divided among the holders who DID claim, pro-rata by their ALLOCATIONS — floor(unclaimed × allocated ÷ claimed) in BigInt, never by holder counts and never by pricing the balances a second time. The second division floors like the first, so its dust stays unclaimed beside the first division's dust: redistributed + remaining unclaimed always equals the unclaimed total, and final paid + remaining unclaimed + undistributed always equals the pool. A holder who did not claim receives no redistribution, a claimant allocated nothing has no base to share by, nobody claiming means there is no one to redistribute to, and everybody claiming means there is nothing to redistribute — both stated, not refused. The redistributed share is derived from the BigInt amounts. Local model only — PRISM distributes nothing, holds no pool, pays no claim, redistributes nothing, and runs no claim window; a real design that redistributes must disclose that choice before the window opens — who counts as a claimant, that the split is by allocation, and what happens to the second division's dust — and redistribution is one destination among several (treasury, burn, or a later window), exactly as modeled. |
| Holder distribution second claim window model | The other destination the claim-window model names for unclaimed allocations — a later window, priced end to end: the claim-window model is composed unchanged, and each holder who missed the first deadline may claim their OWN allocation in the second window, in full and never a share of anyone else's. Local model only — PRISM distributes nothing, holds no pool, pays no claim, and runs no claim window; a real design that opens a second window must disclose it before the first window opens — its deadline, who may claim late, and where allocations still unclaimed after it go (treasury, redistribution, or burn), exactly as modeled. |
| Holder distribution treasury sweep model | The final disposition the second-window model names for the allocations still unclaimed after both claim windows — the design sweeps them to its treasury, priced end to end: the second-window model is composed unchanged, each never-claimed holder's whole allocation is swept in full on top of a treasury balance the design states, and the treasury's final balance is part of the accounting. ## The boundary of this release

**This is a design and research workspace, not a token issuer, lending platform, or deployed ZK application.**

- CIP-113 was present in the upstream repository when checked on **2026-10-04**, with frontmatter status **Proposed**. A merged specification is not a network-wide deployment or certification.
- PRISM’s manifest is an application-specific design format. It is **not** a CIP-defined registry datum, compiled Plutus blueprint, token policy, signed transaction, or minted asset. The registry entry preview is likewise application-specific: it contains no policy ID, datum encoding, or on-chain registration.
- Transfer and eligibility tests run in JavaScript. They do not execute on-chain scripts, check spendable balances, verify identity, or generate zero-knowledge proofs.
- The Midnight wallet connector is real. A Compact circuit, deployed contract, proof service, issuer / revocation system, and Cardano attestation verifier are **not deployed** by PRISM.
- PRISM has no affiliation with RealFi, Midnight, or the Cardano Foundation. RealFi interactions happen at [app.realfi.co](https://app.realfi.co/); scenario rates are fictional inputs, not product rates.
- No wallet transaction signing, message signing, transaction submission, asset custody, minting, redemption, staking, or payment initiation is implemented.
- The Foundation’s reference platform identifies itself as R&D with an independent security audit pending. Review and pin all dependencies before implementing a production system.

## Run locally

Requires Node.js 22 or newer. There are **no npm dependencies and no install step**.

```sh
git clone https://github.com/Kshot3000/Grok-CIP-113.git
cd Grok-CIP-113
npm test
npm run dev
```

Open `http://localhost:4173`. Run `npm run build` for a static `dist/` directory. The site supports a repository subpath and uses hash navigation, so deep links work on GitHub Pages without server rewrites.

## GitHub Pages

The included workflow runs tests, builds the site, and publishes `dist/` on pushes to `main`.

If this is the first deployment, set **Settings → Pages → Source → GitHub Actions**. The workflow also requests automatic enablement; if repository permissions prevent that, enable Pages in settings and rerun the workflow. No personal access token or paid service is needed.

## Configuration

`src/config.js` contains creator identity, the donation address, verified source URLs, network endpoints, and optional registry API configuration. Change the `site` URL if hosting elsewhere.

`registryApi` is intentionally empty. To enable registry reads, set it to the HTTPS origin of your hosted, Foundation-compatible programmable-token backend, with CORS for your site. PRISM calls the read-only `GET /api/v1/registry/protocols` endpoint and validates its basic response shape. An indexer is authoritative only for the deployments and network it actually indexes; independently verify deployment identity.

Do not put Blockfrost tokens, mnemonics, signing keys, or service secrets in frontend configuration. This website needs none.

## Data, privacy, and networks

- Network data comes directly from Koios for the selected network. Failed requests display an unavailable state; old or fictitious values are not presented as live. A block older than five minutes is labeled delayed.
- The Preview reference is repository configuration, not an assertion that an address is safe, current, funded, or deployed. The bundled reference was checked on 2026-10-03 and is explicitly marked as a snapshot if refresh fails.
- A Cardano wallet exposes mainnet versus testnet via CIP-30. It cannot establish which testnet the user selected. Confirm Preview versus Preprod in the wallet.
- Wallet state is kept in memory. Only a valid design is saved to local storage. No analytics or tracking cookies are included. Local draft persistence may be unavailable in restricted browser modes; JSON export remains available.
- The eligibility sandbox does not save or transmit its fictional input values. Do not enter real personal data.
- Public API providers and external sites receive ordinary network requests when used. Wallet permission is requested only after a user chooses to connect. App disconnection clears PRISM state; revoke permissions inside the wallet to fully remove access.
- Donation copy and QR contain the exact user-supplied Cardano mainnet address. PRISM never initiates the transfer.
