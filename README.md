# PRISM · Cardano programmable token studio

**Your asset. Your rules.** An open-source workspace for exploring CIP-113 programmable assets, real-world finance, and privacy-aware eligibility.

Built by **[KShot · @kshot9000](https://x.com/kshot9000)** for the Cardano community.

**[Open the website](https://kshot3000.github.io/Grok-CIP-113/)** · **[CIP-113 specification](https://github.com/cardano-foundation/CIPs/tree/master/CIP-0113)** · **[Report an issue](https://github.com/Kshot3000/Grok-CIP-113/issues)**

## What works

| Workspace | Functionality |
| --- | --- |
| Token studio | Six editable templates — real-world asset, private credit, stablecoin concept, community access, carbon credit (indivisible tonnes, KYC-gated), and event ticket (open access with a four-per-transfer anti-scalping cap) — validated token identity and precision, configurable allowlist / transfer cap / issuer controls / eligibility, and exact BigInt transfer modeling. The Test step also has a sequence lab: transfers run in order against a modeled ledger (the issuer starts holding the full designed supply), each step checked for sender balance, access, the per-transfer cap, issuer controls, and eligibility — a blocked step moves nothing and later steps are still evaluated, so the knock-on effect of a denial is visible in the final balances. A custom builder sits next to the presets: start from the preset you were viewing, then change senders, recipients, and amounts, add steps (up to 12), reorder them, or remove them, and run your own order against the same modeled ledger. |
| Substandard lab | Each template presets a CIP-113 Layer-3 substandard — freeze-and-seize, KYC, or KYC extended from the Foundation reference platform (community template uses PRISM’s generic rules). The Test step models the modules’ documented checks one by one: denylist on both parties, authorised-only seizure, the five sender-certificate checks, recipient allowlist membership and expiry, and the self-transfer exemption. Local simulation only; legacy design files without a substandard import as generic. A lifecycle panel runs transfers, denylist updates, and seizures in order against one modeled ledger and one evolving denylist — a holder listed mid-flight loses both transfer directions and becomes seizable, and removal restores transfers and ends the seizure authority again; only the module's own checks are modeled there, not the design's generic toggles. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds (switching a kind converts the step — an amount is kept where both kinds carry one, and a denylist update carries no amount), accounts, actors, and amounts, add transfer, denylist-update, or seizure steps (up to 12), reorder them, or remove them, and run your own lifecycle against the same model. The KYC-extended lab has its own lifecycle panel: transfers carrying a modeled certificate state (valid, missing, untrusted, invalid signature, naming another sender, or expired) run in order against one modeled ledger, one evolving recipient allowlist, and the module's global pause — an entry expiring mid-flight blocks the same transfer its renewal restores, a pause blocks every transfer whatever its certificate says, and each transfer is judged by the same checks as the single-shot lab, fed with the allowlist and pause as they stand at that step. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds, accounts, certificate states, entry states, and amounts, add steps (up to 12), reorder them, or remove them — switching a step's kind converts it to the new kind's defaults, and a removal carries no entry state, so its expired flag is dropped rather than carried into a later listing. The basic-KYC lab has its own lifecycle panel: transfers carrying a modeled certificate state (valid, missing, invalid signature, naming another sender, or expired) and naming the modeled entity that signed it run in order against one modeled ledger, one evolving trusted-entity list (KYC entity A starts trusted, entity B does not), and the module's global pause — an entity removed mid-flight leaves earlier transfers applied but its later certificates fail on the trusted-entity check alone, a second entity added mid-flight starts passing, and recipients are never checked, since basic KYC checks the sender only. A custom builder sits next to its presets: start from the preset you were viewing, then change step kinds, accounts, certificate states, signing entities, and amounts, add transfer, trust-update, or pause steps (up to 12), reorder them, or remove them — switching a step's kind converts it, keeping the modeled entity where both kinds name one (a transfer's signer becomes a trust update's subject, and back) and starting every other field from the new kind's defaults. |
| Supply lab | The Test step also models supply changes (issuance): the designed supply is an *initial* supply, so the lab runs a mint or a burn attempted by the issuer or by someone else, checked for issuance authority and for exact BigInt supply bounds — a mint may not pass the signed 64-bit asset ceiling (landing exactly on it is allowed, one base unit past it is blocked) and a burn may not exceed what was issued (burning the whole supply ends at exactly zero). The per-transfer cap is deliberately *not* applied: it gates transfers, not issuance. Labeled in the UI as PRISM's generic issuance model — not a Foundation substandard module, and a real token's issuance logic defines its own authority. No tokens are minted or burned. A supply sequence panel chains changes in order against a running modeled supply, so a burn creating int64-ceiling headroom a later mint can use (and a blocked change leaving the supply intact for later steps) is visible step by step; a custom builder sits next to its presets — start from the preset you were viewing, then change actions, actors, and amounts, add steps (up to 12), reorder them, or remove them, and run your own issuance schedule against the same model. A timeline lab then interleaves the two: transfer steps and supply steps run in one order against one modeled state — a ledger of balances plus the supply those balances always sum to — so minted tokens become transferable in the same timeline, and a burn draws on the issuer's modeled holding (tokens already distributed to other modeled accounts are not the issuer's to burn, so a burn can be blocked by the issuer's balance even when the total supply would cover it). Transfer rules gate only the transfer steps and issuance checks only the supply steps; a blocked step changes nothing and later steps still evaluate. A custom builder sits next to its presets — start from the preset you were viewing, then change step kinds (switching a kind converts the step, keeping its amount), senders, recipients, actions, actors, and amounts, add transfer or supply steps (up to 12), reorder them, or remove them, and run your own timeline against the same one-state model. |
| Learn CIP-113 | An eight-lesson plain-language learning path paraphrased from the official spec — why programmable tokens exist, shared-custody smart wallets, the withdraw-zero pattern, the registry, substandards, third-party actions / unfracking, protocol upgradability (re-pointable wiring, the immovable base credential, and the two-phase nomination → promotion authority handover), and programmable tokens in DeFi and wallets (the integration duties, and why a protocol checks the substandard before accepting a token as collateral) — each lesson naming its spec section. Plus a status tracker reproducing the spec’s frontmatter and its own “Path to Active” acceptance checklist verbatim (all four boxes unchecked while the status is Proposed), with the Foundation reference’s R&D / audit-pending caveat kept in place. Status snapshot re-verified against upstream on 2026-10-09. |
| Design review | The Design step ends with a live local review of the design's own coherence, recomputed on every edit: validation blockers, rule coverage (a design with no active rules warns it behaves like an ordinary native token), cap effectiveness (a cap equal to the whole supply warns it can never block a transfer; otherwise the cap's exact BigInt share of supply is shown), the pause state the design would start in, alignment between the generic toggles and the chosen substandard's documented checks (KYC extended expects a recipient allowlist; basic KYC checks the sender only), supply headroom against the signed 64-bit ceiling, and indivisibility at 0 decimals. Labeled in the UI as a local review — not a security audit, not validator review, and no guarantee a design is safe or deployable. |
| Design files | Local draft persistence, versioned JSON export, validated import, and developer handoff. Imports are integrity-verified: amounts must be exact decimal strings (JSON numbers are rejected outright — JSON parsing would round them past 2⁵³ and silently change the supply), the token summary must match the design field by field, the implementation section is cross-checked against the design too — its named substandard (id, name, reference, and modeled-locally flag), its Midnight mode (derived from the design's eligibility toggle), and its required developer-handoff steps must all match what PRISM exports, so a file edited to name a different module than the design models, misstate its eligibility plan, or drop the independent security review from its required steps is rejected — and a manifest claiming a deployed status, an Active CIP-113, a verified Midnight proof, a deployed bridge, or a RealFi affiliation/product is rejected instead of imported. Files whose status/implementation sections were hand-trimmed away still import (a design section that never stated a substandard still migrates to the generic module, its implementation copy uncross-checked); whitespace around names and amounts is canonicalised. A design file can also be verified without opening it: the Export step's Verify button runs exactly the import's checks and reports the design the file describes — identity, exact base-unit supply and limit, rule toggles, substandard, network, and whether an implementation section was present to cross-check — while your current design and saved draft stay untouched; the verifier returns no design to apply, so verifying can never become a quiet import, and a file that fails any check is refused whole. A design file can also be compared to the design currently open, without importing it: the Export step's Compare button runs the same verification, then reduces both designs through the verifier's own summary builder and reports every differing field — network, identity, exact base-unit supply and limit, rule toggles, starting pause state, template, and substandard (one field, not two) — in a fixed order, with the file's value and yours side by side; file metadata (the file's stated export time, whether an implementation section was present) is reported separately and never counts as a difference, two exports of the same design at different times compare as identical, and the comparison likewise returns no design to apply. No server account is required. |
| Registry entry preview | The Export step also renders a deterministic, application-specific preview of the design information a CIP-113 registry entry would need to describe — token identity, exact BigInt base units, transfer policy, and substandard — alongside an explicit list of what only a real deployment can supply (policy ID, registry node position and proofs, Plutus Data / CBOR encoding). Labeled “NOT A CIP DATUM” in the UI; PRISM registers nothing. A preview file you were handed can be verified in the same step: its honesty flags (application-specific, not a CIP datum, not registered) must state exactly what a preview is, amounts must be canonical exact decimal strings (a JSON number or a padded string is rejected, never converted) with a per-transfer limit no larger than the supply, the substandard section must match PRISM’s catalog field by field, the still-required list and note must match the canonical text when present, and any field a preview never carries — a policy ID, a CBOR encoding, a datum hash — is refused outright. Hand-trimmed files may omit the flags, list, or note (absent is tolerated, contradicting is rejected); the verifier returns the canonical preview and, like the manifest importer, verifies only the file’s internal consistency — it imports nothing, registers nothing, and changes no design. A handed preview can also be compared to the open design’s preview in the same step: comparison runs the verifier first (a file that fails verification is refused whole, never partially compared), then reports differences across ten fields in a fixed order — network, token name, ticker, decimals, initial supply in exact base units (compared bit-for-bit past 2^53), transfer access, per-transfer limit (null when no limit is set), issuer-pause and eligibility modeling, and the substandard as one field. The honesty flags, still-required list, and note are verified rather than compared — the verifier canonicalises them, so a hand-trimmed file omitting them compares as identical to its own full export — and the return carries the two canonical previews and the differences only, no design object, so comparing cannot become a quiet import either. |
| Cardano wallets | Real CIP-30 discovery and permission flow, network checks that name the expected network (CIP-30 reports only mainnet vs testnet, so Preview vs Preprod is confirmed in the wallet), rejection of malformed network ids and incomplete wallet APIs, public payment address, account-change detection, and app disconnection. On connect, an address book is also read locally from the wallet's optional CIP-30 lists (used / unused / reward addresses): every entry is decoded in the browser, counted by kind, checked against the connected network (mismatches flagged, never hidden), matched against the CIP-113 smart-wallet shape with the usual shape-is-not-membership caveat, and the reward (stake) credential is compared with the payment addresses' stake credential. A list a wallet does not offer is shown as unavailable, never guessed; no balance is read. Read only. |
| Network explorer | Live Koios chain tip and native asset lookup, refresh and failure states, no invented metrics. The registry panel can also verify the Foundation’s pinned Preview reference deployment live: the platform repository’s configuration is fetched fresh and must match the pinned script hash and protocol policy field by field, and Koios Preview must confirm that exact deployment transaction in a block with valid contract execution, before anything is shown as confirmed. Registry browsing still requires a Foundation-compatible indexer, which is not connected. |
| Registry proof planner | The registry panel also plans CIP-113 registry proofs locally against a modeled registry list you supply: for each distinct policy a transfer would touch, in lexicographic order, it names the proof the spec requires — the policy's own registry node as a TokenExists proof when the policy is in the list, or the covering node as a TokenDoesNotExist proof when it is not (the node whose key is the largest key below the policy and whose `next` is above it, after which the asset is treated as an ordinary native token). The modeled list is validated as the on-chain list is built — every key exactly 28 bytes, each key once, strictly increasing — and a list breaking those invariants is refused rather than silently sorted. A policy sorting before the first key, after the last key, or into an empty list has no covering node in the list given and is reported that way: a real registry carries those cases on its origin or terminal node, which is deployment data the model does not invent. The UI states the plan proves a policy's status only against the modeled list — PRISM reads no live registry here. Anchored on the spec's own worked example (registry [A, C, E], policy D proved absent by covering node C). |
| Registry proof list verifier | The checking half of the proof planner, in the same registry panel: a proof list a transaction claims to carry (one line per proof — policy, type, node index, node key, optional next key) is verified locally against the same modeled registry and policies, against the spec's three requirements at once — completeness (exactly one proof per distinct policy touched; missing, extra, and duplicate proofs each named), ordering (the list in the policies' lexicographic order, judged on the claimed sequence as given), and correctness (proof type, node index, node key, and stated next key each get their own verdict, so a failure names the position to re-check; claiming a registered policy is absent — the bypass the mechanism exists to prevent — fails the type verdict). The expected proofs are the planner's own output, so planning and verification cannot disagree. A claimed proof that cannot be read (malformed ID, unknown type, non-integer index) is refused, never scored as a wrong proof; a policy the modeled list cannot prove is reported unverifiable in this model, claimed or not, because a real registry carries those cases on origin/terminal nodes this model does not invent. The UI states a valid verdict proves only that the list satisfies the three requirements against the modeled list — PRISM reads no live registry and inspects no transaction. |
| Registry change impact | The temporal half of the proof planner and verifier, in the same registry panel: two modeled registry lists — the registry as it was and as it would be after a change — are compared locally, per distinct policy a transfer would touch, and each proof is classified as unchanged, proof changed (with the exact positions that moved: status, proof type, node index, node key, next key), newly registered, no longer registered, newly provable, or newly unprovable, alongside the keys added and removed. An insertion shifts the node index of every key after it, a registration turns an absence proof into an existence proof, and a removal can strand a policy past the new last key — so a proof list planned against the old registry can fail for reasons that have nothing to do with the policies themselves, and this comparison names which proofs survive. Both lists are planned through the planner itself, so the comparison inherits its disciplines: each list is refused if it breaks the registry invariants (28-byte keys, each once, strictly increasing), and a policy with no covering node in a list is reported unprovable in that model rather than invented over — a real registry carries those cases on its origin or terminal node. The UI states the comparison is between the two modeled lists entered — PRISM reads no live registry, and neither list is one. |
| Registry insertion planner | The constructive half of the registry panel: registering a programmable token inserts one node into the registry's sorted linked list, and the insertion is planned locally against the same modeled registry — the node the registering transaction must spend (prev_node: the planner's covering node for an unregistered policy), that node returned with only its `next` rewritten to the new key, the new node pointing at prev_node's old `next`, its index in the resulting list, and exactly which existing keys shift index. The boundary cases are planned honestly rather than refused: a policy sorting before the first key is preceded by the registry's origin node — real on chain, but deployment data the modeled list does not contain, so its key is not shown — and a policy after the last key spends the last node itself while the new node inherits that node's old `next`, the list's terminal value, which the model does not carry or invent. A policy already in the list is reported already registered, naming the node it occupies. The plan states what a real registration additionally requires — the RegistryInsert redeemer naming the key and the minting logic credential (which the validator binds to the key cryptographically), and the registry NFT minted under the registryMintingPolicy with the policy as its name — and that PRISM read no live registry, built no transaction, and registered nothing. Cross-checked in tests both ways: the planner finds the inserted policy registered at the planned index in the resulting list, and the change-impact diff classifies it newly registered. |
| Registry insertion verifier | The checking half of the insertion planner, under it in the same registry panel: a claimed insertion — the prev_node a registering transaction is said to spend, the `next` it is said to return that node with, the `next` the new node is said to point at, and the new node's claimed index — is checked locally, position by position, against the planner's own plan for the same modeled registry and policy, so a failure names exactly which part of the claimed insertion breaks the chain (spending the right node but pointing the new node at the wrong successor fails only the new-next position). An unstated position is reported not-stated and the claim incomplete, never passed and never failed — while `origin` and `terminal` are statements (a null prev_node or a null new next) and are judged true or false like any key. A policy already in the modeled list is reported not insertable, with no claim scored against it, and a malformed claim (a key that is not a 28-byte policy ID, a fractional index) is refused rather than reported as a wrong insertion. A correct verdict proves only the list mechanics against the modeled list entered: the RegistryInsert redeemer's minting logic credential, its cryptographic binding to the key, and the registry NFT are issuer and deployment data no modeled list carries, so they are not judged — and PRISM read no live registry, inspected no transaction, and registered nothing. |
| Registry insertion comparison | The comparison counterpart to the insertion planner and verifier, under them in the same registry panel: the insertion planned for one policy against the modeled registry is compared with the same policy planned against an after list — another policy registering first, a key inserted, a key removed — across exactly four positions (status, insertion index, prev_node, node next), each side planned by the insertion planner itself so comparison and planning can never disagree about where the policy belongs in either list. The change is classified by its registration story first (newly registered, no longer registered), then by whether an existing node or a still-planned insertion moved. What is deliberately not compared: the plan's successor key restates its new node's next, so a removed successor counts once, never twice, and the shifted-keys list is derived from the index and the list itself. `origin` and `terminal` name real on-chain values neither modeled list carries. Compared locally between the two lists entered — PRISM read no live registry, applied no insertion to either list, and registered nothing. |
| Registry node datum checker | The content half of the registry panel, under the insertion verifier: a RegistryNode datum — the seven fields every registry entry carries, in the spec's load-bearing order (key, next, minting / transfer / third-party / unfracking logic credentials, global_state_cs) — is checked locally, field by field, against the spec's datum rules and the Foundation reference implementation's pinned values. A key must be a 28-byte policy ID, with one exception: the canonical origin node, whose key is the empty bytestring and whose four credentials are all the empty public-key credential — an empty key in any other shape is a broken datum, not an origin node. Next must be a 28-byte successor sorting strictly after the key, or the reference implementation's terminal sentinel — thirty bytes of 0xff, deliberately not 28, so it sorts after every 28-byte policy ID including an all-0xff one. Each logic credential must carry a 28-byte hash, except unfracking, where the empty public-key credential is a meaning, not a defect: it forbids unfracking for that policy (least permission), while a public-key hash makes it signature-gated and a script hash delegates it to the issuer's hook. A global_state_cs of 28 bytes means every transfer must carry the global-state UTxO as a reference input; empty means none is expected. A datum that cannot be read at all (a missing or unknown field, an unknown credential kind, non-hex bytes) is refused rather than scored in part. A datum meeting every rule is still not a registration: the checker reads no Plutus Data or CBOR, inspects no UTxO, and does not judge the registry validator's cryptographic binding of the minting logic to the key or the registry NFT the node must hold. Pinned in tests against the reference implementation's canonical origin node and sentinel, including the all-0xff-key chain case. |
| Registry node datum builder | The producing half of the checker above, in the same panel: when — and only when — every field meets the spec, the datum itself is built and shown under the spec's field names in the spec's load-bearing order (key, next, minting_logic_script, transfer_logic_script, third_party_logic_script, unfracking_logic_script, global_state_cs), credentials as kind + hash pairs, hex canonicalised to lowercase, ready to carry into a builder's own registration tooling. The builder judges its input with the checker itself, so the two can never disagree: a readable datum breaking any field rule — or the chain order — is refused with the failing fields named in the checker's own words, never built in part, and an unreadable datum is refused on the checker's terms. The origin inputs build exactly the reference implementation's canonical origin node. Building is not registering: the return carries no Plutus Data or CBOR encoding and no registry NFT, and PRISM registers nothing — the validator's cryptographic binding of the minting logic to the key remains a registration-time check no local builder can perform. |
| Registry node datum reader | The reading-back half of the builder above, in the same panel: paste a built datum's JSON and it is parsed and judged again before it is trusted. The parser reads only the serialized form — the seven fields under the spec's names, in the spec's load-bearing order (a reordered, renamed, missing, or extra field is refused, never silently re-sorted or repaired; a smuggled CBOR, datum-hash, or registry-NFT field is precisely the edit it exists to refuse), each credential naming kind then hash — and judges the converted datum by calling the builder itself, so parse, build, and check can never disagree and a genuine built datum round-trips exactly. A readable datum breaking any field rule, or the chain order, is refused with the failing fields named in the checker's own words, never read back in part. Reading back is not registering: the JSON is PRISM's serialization, not Plutus Data or CBOR, and no UTxO, registry NFT, or live registry is read. |
| Registry node datum comparison | The comparison counterpart to the reader above, in the same panel: a handed built datum is compared field by field against the node entered in the checker — did the successor move, or a logic credential too? The handed side is judged by the parser itself and the current side by the builder itself, so the comparison can never disagree with reading back, building, or checking about what either datum says: a datum that would fail reading back fails comparison with the same reason, refused whole and never partially compared, and a current node that does not build is refused as the current side. Seven fields in the spec's order, each logic credential counted as one field (its kind and hash together), and the builder's derived summaries — node kind, unfracking mode, global state — are never counted again, since they move with their fields. Values compare in the canonical form the builder writes, so a copy differing only in hex case compares as identical. Comparing is not registering: no live registry is read, no Plutus Data or CBOR is decoded, and neither datum is applied anywhere. |
| BaseSpendRedeemer hint planner + verifier | Past the registry panel's datum checker, the delegation chain's redeemer is planned and verified locally: every programmable-token input runs programmableLogicBase, which locates the protocol parameters UTxO among the transaction's reference inputs and requires the withdraw-zero of the programmableLogicGlobal credential that UTxO's datum names — addressed by the redeemer's two hints, params_idx and wdrl_idx. The planner computes both for a modeled transaction: params_idx is the parameters UTxO's position in the reference inputs as listed (the ledger does not reorder reference inputs), while wdrl_idx is the global credential's position in the withdrawal map AS THE LEDGER ORDERS IT — script credentials first, bytewise within each kind, then public-key credentials — so a builder who counts insertion order instead points the hint at the wrong credential whenever a public-key withdrawal was inserted first or script credentials were inserted out of byte order, and the spend fails; the preloaded example demonstrates exactly that trap (the global credential is inserted last and sits first in the ledger order). A readable transaction missing the parameters reference or the global withdrawal is reported unplannable, with the missing piece named and no index invented; a transaction that cannot be read (a duplicated reference input or withdrawal credential, a credential hash that is not 28 bytes) is refused. The verifier judges a claimed redeemer hint by hint against the planner's own output, showing what a wrong hint actually resolves to; an unstated hint is incomplete, never passed and never failed, and a malformed hint is refused rather than scored. A correct pair proves only that the hints resolve against the modeled lists entered — PRISM reads no transaction, no parameters UTxO, and no chain state, and the action delegate, registry proofs, and each token's logic withdraw-zero are separate requirements not judged here. |
| BaseSpendRedeemer comparison | The comparison counterpart to the planner and verifier above it: transactions change while they are being assembled — a reference input is added ahead of the parameters UTxO, a withdrawal joins, the parameters UTxO is dropped — and a redeemer planned against the earlier version resolves to the wrong input or the wrong credential in the later one. The comparison plans BOTH modeled versions through the planner itself, so it can never disagree with planning about either hint in either version, and a version that cannot be read is refused with the planner's reason, never compared around. It tracks ONE redeemer: the two versions must name the same protocol parameters reference and the same programmableLogicGlobal credential (compared in the planner's canonical form, so hex case alone is the same credential); different targets are different redeemers and are refused rather than scored. Three positions are compared — the status and the two hints the redeemer actually carries. The plan's insertion-order position is deliberately NOT one of them: it is not carried by the redeemer, and a pure reordering of the withdrawal insertions changes it while the ledger order, and therefore wdrl_idx, stands exactly still, so that reordering compares as unchanged; a public-key withdrawal inserted first likewise moves no hint, because the ledger orders public-key credentials after every script credential. The change is classified by its plannability story first (became unplannable / became plannable), then still-unplannable-differently and hints-changed; which pieces are missing needs no position of its own, since it is exactly which hints are null. The lists' own change is reported separately as the added and removed reference inputs and withdrawal credentials, never counted as positions. Comparing proves only how the modeled change moves the modeled hints — PRISM reads no transaction and no chain state, and no redeemer is applied to either version. |
| Delegate pairing planner + verifier (third-party / unfracking) | The other two CIP-113 actions share one delegate redeemer — ThirdPartyRedeemer and UnfrackingRedeemer both name a registry_node_idx (the acted-on policy's RegistryNode among the reference inputs as listed) and an outputs_start_idx (where the paired continuing outputs begin). The planner walks a modeled transaction's inputs in order and pairs every programmableLogicBase input with the next consecutive output from outputs_start_idx; inputs at other addresses are skipped and consume no output, so counting inputs instead of base inputs misaligns every pair after the first skipped input (the preloaded example's base inputs sit at positions 1, 2, and 4 and pair with outputs 1, 2, and 3). Outputs before the start pair with nothing, but for a third-party action the acted-on policy's tokens they hold at base addresses still count toward the output side of the balance invariant — counted and reported separately. A readable transaction whose pairing cannot be completed (the acted-on node is not among the reference inputs, the start points past the last output, or too few outputs remain, with the shortfall named) is reported unplannable with no index or pair invented; a transaction that cannot be read (an unknown action, a duplicated reference input, an entry that does not say whether it sits at a base address) is refused. The verifier judges a claimed redeemer hint by hint against the planner's own output — a start off by one shifts every pair and fails that position alone — with an unstated hint incomplete and a malformed hint refused. A correct pairing proves only the pairing against the modeled lists entered: PRISM reads no transaction, no registry, and no chain state, and the delegate's per-pair checks (same address and datum, other policies byte-identical, the acted-on policy actually changing for third-party or stripped entirely for unfracking, the logic withdraw-zero, the balance invariant) are not judged here. |
| Delegate pairing comparison | The comparison counterpart to the planner and verifier above it: transactions change while they are being assembled — a reference input is added ahead of the acted-on node, an input or output joins, the RegistryNode is dropped — and a delegate redeemer planned against the earlier version resolves to the wrong node, or begins the pairing at the wrong output, in the later one. The comparison plans BOTH modeled versions through the pairing planner itself, so it can never disagree with planning about either hint in either version, and a version that cannot be read is refused with the planner's reason, never compared around. It tracks ONE redeemer: the two versions must name the same action and the same acted-on policy's RegistryNode (a third-party redeemer and an unfracking redeemer share a shape but are not the same redeemer); different targets are refused rather than scored. Three positions are compared — the status and the two hints the redeemer actually carries. The pairs themselves are deliberately NOT one of them: they are derived by the delegate walking the inputs, so a change that adds a base input (with the outputs to pair it) or inserts a non-base input ahead of the base ones changes the pairs while both hints stand exactly still — the new base input pairs automatically — and that pairing change is reported separately, never counted as a position; which pieces are missing needs no position either, since a missing node is exactly a null registry_node_idx and an output shortfall differs on the status alone. The change is classified by its plannability story first (became unplannable / became plannable), then still-unplannable-differently and hints-changed, and the reference list's own change is reported as the added and removed reference inputs. Comparing proves only how the modeled change moves the modeled hints — PRISM reads no transaction, no registry, and no chain state, and no redeemer is applied to either version. |
| Transfer output-value calculator + verifier | The TransferAct half of the delegation chain, under the delegate pairing tools: the expected output value at programmableLogicBase addresses is calculated locally per asset — validated input value plus validated mint value, the mint signed, so the spec's own examples hold exactly (input 100, burn 30, expected 70; input 100, mint 50, expected 150). Only policies proven registered (TokenExists) enter the accumulator — an unvalidated policy's input and mint are reported as excluded ordinary native tokens, never counted — several spent UTxOs holding one asset sum, while tx.mint listing one asset twice is refused (a value map holds each asset once), quantities are BigInt-exact decimal strings bounded by the modeled int64 ceiling, and a burn past the validated input is unplannable with the negative arithmetic shown, never clipped to zero. | Transfer output-value comparison | The comparison counterpart to the calculator and verifier above it: transfers change while they are being assembled — a spent UTxO joins, a burn is adjusted, a policy's registry proof arrives or is withdrawn — and outputs already built against the earlier expectation then fail the delegate's floor in the later one. The comparison plans BOTH modeled versions through the calculator itself, so it can never disagree with planning about any asset's expected value in either version, and a version that cannot be read is refused with the calculator's reason, never compared around. One position is compared per validated asset — its expected quantity, the one number the delegate checks the outputs at base addresses against. The input and mint quantities are deliberately NOT positions of their own: they are the expectation's components, so counting them would double-count a single move, and a change whose components cancel (input up 10, mint down 10) leaves the expectation — and every output built against it — exactly where it stood, comparing as unchanged for that asset with the composition change reported separately, never counted. Each asset is classified by its plannability and presence story first (became unplannable / became plannable, still-unplannable-differently, newly expected, no-longer expected, newly validated, no-longer validated), then expected-changed, with quantities compared as exact BigInt decimal strings past 2^53. | Protocol upgrade planner + verifier | The spec's protocol upgradability, under the transfer output-value tools — the last CIP-113 mechanism PRISM had not modeled: a deployment's credentials live in the protocol parameters datum as data and are read live at validation time, so the programmableLogicGlobal credential, the protocol-level issuance logic, and the three action delegate credentials can be re-pointed for every programmable token at once without redeploying anything, while the programmableLogicBase credential must not move (it is the payment credential of every smart-wallet address in the deployment — moving it would relocate every holder's funds; a different base is a different deployment) and an individual token's minting policy is likewise permanent. ## The boundary of this release

**This is a design and research workspace, not a token issuer, lending platform, or deployed ZK application.**

- CIP-113 was present in the upstream repository when checked on **2026-10-04**, with frontmatter status **Proposed**. A merged specification is not a network-wide deployment or certification.
- PRISM’s manifest is an application-specific design format. It is **not** a CIP-defined registry datum, compiled Plutus blueprint, token policy, signed transaction, or minted asset. The registry entry preview is likewise application-specific: it contains no policy ID, datum encoding, or on-chain registration.
- Transfer and eligibility tests run in JavaScript. They do not execute on-chain scripts, check spendable balances, verify identity, or generate zero-knowledge proofs.
- The Midnight wallet connector is real. A Compact circuit, deployed contract, proof service, issuer / revocation system, and Cardano attestation verifier are **not deployed** by PRISM.
- PRISM has no affiliation with RealFi, Midnight, or the Cardano Foundation. RealFi interactions happen at [app.realfi.co](https://app.realfi.co/); scenario rates are fictional inputs, not product rates.
- No wallet transaction signing, message signing, transaction submission, asset custody, minting, redemption, staking, or payment initiation is implemented.
- The Foundation’s reference platform identifies itself as R&D with an independent security audit pending. Review and pin all dependencies before implementing a production system.

## Run locally

Requires Node.js 22 or newer. There are **no npm dependencies and no install step**.

```sh
git clone https://github.com/Kshot3000/Grok-CIP-113.git
cd Grok-CIP-113
npm test
npm run dev
```

Open `http://localhost:4173`. Run `npm run build` for a static `dist/` directory. The site supports a repository subpath and uses hash navigation, so deep links work on GitHub Pages without server rewrites.

## GitHub Pages

The included workflow runs tests, builds the site, and publishes `dist/` on pushes to `main`.

If this is the first deployment, set **Settings → Pages → Source → GitHub Actions**. The workflow also requests automatic enablement; if repository permissions prevent that, enable Pages in settings and rerun the workflow. No personal access token or paid service is needed.

## Configuration

`src/config.js` contains creator identity, the donation address, verified source URLs, network endpoints, and optional registry API configuration. Change the `site` URL if hosting elsewhere.

`registryApi` is intentionally empty. To enable registry reads, set it to the HTTPS origin of your hosted, Foundation-compatible programmable-token backend, with CORS for your site. PRISM calls the read-only `GET /api/v1/registry/protocols` endpoint and validates its basic response shape. An indexer is authoritative only for the deployments and network it actually indexes; independently verify deployment identity.

Do not put Blockfrost tokens, mnemonics, signing keys, or service secrets in frontend configuration. This website needs none.

## Data, privacy, and networks

- Network data comes directly from Koios for the selected network. Failed requests display an unavailable state; old or fictitious values are not presented as live. A block older than five minutes is labeled delayed.
- The Preview reference is repository configuration, not an assertion that an address is safe, current, funded, or deployed. The bundled reference was checked on 2026-10-03 and is explicitly marked as a snapshot if refresh fails.
- A Cardano wallet exposes mainnet versus testnet via CIP-30. It cannot establish which testnet the user selected. Confirm Preview versus Preprod in the wallet.
- Wallet state is kept in memory. Only a valid design is saved to local storage. No analytics or tracking cookies are included. Local draft persistence may be unavailable in restricted browser modes; JSON export remains available.
- The eligibility sandbox does not save or transmit its fictional input values. Do not enter real personal data.
- Public API providers and external sites receive ordinary network requests when used. Wallet permission is requested only after a user chooses to connect. App disconnection clears PRISM state; revoke permissions inside the wallet to fully remove access.
- Donation copy and QR contain the exact user-supplied Cardano mainnet address. PRISM never initiates the transfer.

A reward-build suite guards the standalone reward-address builder: a key credential builds the exact type-14 address byte for byte and a script credential the type-15 one (the kind is part of the credential — the same hash under the other kind is a different address), every built address round-trips through the reward inspector in bech32 and CIP-30 hex forms across both networks, the standalone build equals the derivation from a base address for all four base types on both networks, a CIP-113 smart wallet's reward address builds from the owner credential alone for key and script owners, uppercase hashes are canonicalised, and hashes that are short, long, odd-length, or non-hex are refused with their byte count rather than padded, alongside unknown credential kinds and networks. A reward-inspector suite guards the standalone reward-address inspection: all four official CIP-19 reward vectors (types 14 and 15, mainnet and testnet) decode to the published stake-key and script credentials, those credentials are exactly the ones the CIP's published base vectors carry in their stake position (deriving from the base vectors lands on the reward vectors), building from a vector's credential reproduces the vector, the hex form inspects identically apart from the recorded input form with the canonical Bech32 address reported and uppercase hex canonicalised, the no-checksum property is pinned (a changed hex digit decodes to a different credential rather than failing, where the same change in Bech32 fails its checksum), and odd-length hex, payment addresses in either encoding, wrong header types, bad network nibbles, truncated or overlong inputs, and mixed-case Bech32 are all refused. A pointer-address suite guards the inspector's CIP-19 pointer decoding: all four official CIP-19 pointer vectors (types 4 and 5, mainnet and testnet) decode to the published pointer — slot 2,498,243, transaction 27, certificate 3 — with payment credentials equal to the base vectors' payment credentials, custom pointers round-trip across the coordinate grid (group boundaries at 127/128 and 16,383/16,384 included), a script-payment pointer address is not a CIP-113 smart-wallet shape, no reward address is derived from a pointer (the refusal names the certificate's coordinates and the chain lookup it would take), and truncated, missing, trailing-byte, non-canonical, and oversized coordinates are all refused, while Byron and reward addresses remain refused and non-pointer inspections carry a null pointer. A hex-form suite guards the inspector's second encoding: the official CIP-19 base vector and every built type on both networks inspect identically from hex and from Bech32 apart from the recorded input form (with the canonical Bech32 address reported), a pointer address inspects identically from hex, uppercase hex is canonicalised, reward derivation and smart-wallet derivation accept hex inputs, the no-checksum property is pinned (a changed hex digit decodes to a different address rather than failing, where the same change in Bech32 fails its checksum), and odd-length, wrong-length, bad-network, Byron, and reward hex are all refused. An eligibility-cohort suite guards the Midnight page's public-output preview: the default cohort isolates exactly one failing check per participant, cohort results match the single-participant model member for member, a requirement switched off admits exactly the participants it gated, boundary values (score equal to the minimum, age exactly 18) pass, malformed policies and cohorts throw instead of producing a partial public record, and the public output carries no private value under any key — a deep key scan plus a serialized-value scan both come back clean. A Byron-inspector suite guards the legacy decoder: both cardano-wallet worked examples decode to their published roots, types, attributes, and stored checksums (the testnet example's encrypted derivation path and its 1,097,911,063 network discriminant included), the CIP-19 table example and both SLIP-0023 addresses decode with the CRC32 verified against the payload, the module's CRC32 agrees with Node's reference zlib.crc32, script and redemption types and an unrecognised attribute decode from independently constructed addresses (test-assembled CBOR, a zlib CRC32, test-side Base58), and a corrupted checksum, a non-28-byte root, an unknown type, non-canonical CBOR, truncation, and non-Base58 input are all refused — while the payment inspector still refuses Byron addresses. A smart-wallet verification suite guards the Network page's checking half of the derivation tool: a derived smart wallet verifies exactly for key and script owners on both networks and from the hex form of either address, each component verdict is isolated by a candidate differing in exactly that position (wrong base script, wrong owner, the owner's hash under the wrong credential kind, network alone), enterprise and pointer candidates report their empty owner position instead of a generic failure, and undecodable claims (reward, Byron, a non-28-byte script hash, a garbage owner) are refused rather than reported as mismatches. A denylist-lifecycle suite guards the freeze-and-seize lifecycle model: a holder listed mid-flight fails only the sender check outbound and only the recipient check inbound, seizure is impossible before listing and ends on removal with each seizure check failing independently (authority, listing, holder balance), blocked steps leave balances unchanged with visible knock-on balance failures, denylist updates are idempotent state changes recorded in per-step snapshots, the generic toggles (allowlist, cap, pause, generic freeze) provably do not gate the module lab, modeled balances sum to the designed supply at every step, and malformed steps are blocked steps while malformed sequences throw. A denylist-builder suite guards the freeze-and-seize lifecycle's custom editing model: pure add / remove / reorder / update helpers for a three-kind list that never mutate the list being edited, reject unknown kinds, accounts, actors, non-string amounts, a non-boolean listed flag, and fields the step's kind does not carry, hold the 1–12 step bounds, convert a step when its kind is switched (amount kept between transfer and seizure, dropped for a denylist update, defaulted when converting from one), feed the simulator end to end, and pin that listing before funding blocks the identical transfer that listing after funding allows. A KYC-lifecycle suite guards the extended lifecycle model: an entry expiring mid-flight fails only the recipient-entry check while its renewal restores the identical transfer and the expired holder can still send, a certificate expiring and a pause each block independently (the pause whatever the certificate says), a never-listed recipient fails both recipient checks while a self-transfer by an unlisted account skips them, each modeled certificate state fails exactly the checks the single-shot lab names, blocked funding leaves a visible knock-on balance failure, allowlist and pause updates are idempotent state changes recorded in per-step snapshots, the generic toggles provably do not gate the module lab (its pause starts unset whatever the design's generic flag says), modeled balances sum to the designed supply at every step, and malformed steps are blocked steps while malformed sequences throw. A basic-KYC-lifecycle suite guards the trusted-entity lifecycle model: revoking an entity mid-flight fails its later certificates on the trusted-entity check alone and restoring it restores them, revocation is not retroactive, a second entity starts untrusted and is unaffected by revoking the first once added, recipients are never checked and a self-transfer still needs a sender certificate (there is no recipient check to skip), each modeled certificate state fails exactly the checks the single-shot lab names, trust and pause updates are idempotent state changes recorded in per-step snapshots, the generic toggles provably do not gate the module lab, modeled balances sum to the designed supply at every step, and malformed steps (including an 'untrusted' certificate state, which this lab deliberately does not carry — trust is the evolving list) are blocked steps while malformed sequences throw. A basic-KYC-builder suite guards that lifecycle's custom editing model: pure add / remove / reorder / update helpers for a three-kind list that never mutate the list being edited, reject unknown kinds, accounts, certificate states (including the 'untrusted' state this lab deliberately does not carry), entities, non-string amounts, non-boolean trusted / paused flags, and fields the step's kind does not carry, hold the 1–12 step bounds, convert a step when its kind is switched (the modeled entity kept across transfer and trust, everything else dropped or defaulted), feed the simulator end to end, and pin that revoking before funding blocks the identical transfer that funding first allows, and that a signer fails until a trust step built with the helpers names its entity. A substandard-builder suite guards the single-shot labs' custom scenario model: copy / update helpers that validate a scenario against exactly the fields its module's simulator reads (a recipient field on basic KYC, which never checks recipients, is refused rather than ignored), return new objects in canonical field order without mutating the input, refuse unknown, missing, and string-typed flags, and feed the simulators end to end — including the combined failures no preset carries (an expired certificate under a pause facing an unlisted recipient, failing four checks at once) and the seizure combination the presets omit (an unauthorised actor facing a clean holder, failing both checks at once). A pointer-build suite guards the CIP-19 pointer-address builder: building from the official vectors' payment credentials and published pointer reproduces all four official pointer addresses exactly, every built address inspects back to exactly its inputs across a coordinate grid (including the variable-length group boundaries and the largest safe integer), the emitted encoding is canonical at the 0 / 127 / 128 / 16383 / 16384 boundaries, and missing, fractional, negative, non-numeric, or oversized coordinates, short payment hashes, and unknown credential kinds or networks are all refused. An address-verification suite guards the address builder's checking half: the official CIP-19 vectors (types 0, 1, and 2) verify exactly against their published credentials, every built type on both networks verifies against its own inputs in Bech32 and hex, each component verdict is isolated by a claim differing in exactly that position (a wrong payment hash, the right hash under the wrong credential kind in either position, a base/enterprise disagreement in both directions, and a network difference alone, which builds the candidate's cross-network twin), a pointer candidate reports the pointer it carries instead of a stake verdict, a CIP-113 smart wallet verifies as the base address it is, and undecodable candidates (reward, Byron, garbage) and malformed claims (a short hash with its byte count, a dropped stake hash, a missing one) are refused rather than reported as mismatches. A reward-verification suite guards the reward builder's checking half: all four official CIP-19 reward vectors verify exactly against their published credentials in Bech32 and hex (an all-uppercase claim verifies and is stated in canonical lowercase), a reward address derived from a published base address verifies against that address's stake credential, every built reward address verifies against its own inputs across credential kinds and networks, each verdict is isolated by a claim differing in exactly that position (a wrong hash, the right hash under the wrong credential kind, and a network difference alone, which builds the candidate's cross-network twin), a flipped hex digit is a well-formed mismatch while a flipped Bech32 character is refused on its checksum, and payment, Byron, and garbage candidates and malformed claims are refused rather than reported as mismatches.
